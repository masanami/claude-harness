# 利用者が触れる面を試作で先に固める

機能の要件を文書にする前に、利用者が触れる面の試作を作り、`/show-prototype` で人と往復して固め、決定を `docs/features/<slug>/ux.md` に書き出す。要件・受入基準・クリティカル設計の文書化は `/define-feature` が行う。

> **本スキルは対話前提である**。メインセッションで人と往復する。対話相手の人がいない（headless）で起動された場合は、手順 1〜3（媒体の推定・場面の一覧・試作の作成）までを進め、試作を見せる手順 4 の前で停止して報告する。媒体と場面の一覧は人に確かめられないため、推定のまま報告に書く。`ux.md` は書かない。呼び出し元のエージェントを人の代わりにして試作を固めない。

## 入力

テーマや機能名: $ARGUMENTS（無ければ人に聞く）。`{slug}` は機能名をケバブケースにしたもの（例: `task-export`）。`docs/features/<slug>/prototype/` が既にあれば、作り直さずその試作から再開する。

## 手順

### 1. 媒体を決める

マニフェスト・ディレクトリ構成・既存の画面やコマンドの定義と、テーマの文面から媒体（Web・CLI・API・バッチ・ゲームの画面の流れ）を推定し、推定の根拠を添えて人に確かめる。1 つの機能が複数の媒体に触れるなら、触れる媒体をすべて挙げて確かめる。

### 2. 場面の一覧を決める

利用者が通る主要な流れと、そこで出会う状態（通常・空・エラー・権限なし等）を場面の一覧にして人に確かめる。この一覧が手順 4 の固め終わりの判定に使う網羅の基準になる。

### 3. 試作を作る（媒体ごと）

置き場所は `docs/features/<slug>/prototype/`。媒体が 1 つなら直下に置き、複数なら媒体ごとのサブディレクトリ（`web/`・`cli/`・`api/`・`batch/`・`game/`）に分ける。

- **Web**: 静的な HTML。状態ごとに 1 ファイルとし、遷移はリンクで表す。`file://` で開いて動く作りに限る（`<script type="module">`・`fetch`・外部の CDN を使わない。データは HTML に直接書く。通常の `<script>` は使ってよい）
- **CLI**: 場面ごとに、入力したコマンドと出力・エラー時の表示と終了コード・`--help` を Markdown に書く
- **API**: 呼び出しごとに、リクエストとレスポンスの組（正常・エラー・ページング）を書く
- **バッチ**: 入力と出力のサンプル・ログ・通知の文面・失敗したときに運用の担当者が見るものを書く
- **ゲームの画面の流れ**: Web と同じ作りの静的な HTML で、画面の流れ・HUD の配置・操作の割り当て・1 ループを表す。手触り（操作の重さ・テンポ・当たり判定）と見た目（絵・演出）は扱わない

既存の画面・コマンドを変える機能では、変える画面・場面だけを、いまの見た目をおおまかに写して作る。既存の素材は参照してよく、無いもの（画像を含む）は置き場所と大きさを示すプレースホルダーにする。本番のコード・スタイル・技術スタックは取り込まない。本番のデータ・外部サービスに接続しない。

### 4. `/show-prototype` で往復して固める

媒体ごとに `/show-prototype` を順に呼び、試作のディレクトリ（媒体が複数なら媒体のサブディレクトリ）と媒体を渡す。

返ってきた報告を手順 2 の場面の一覧と突き合わせ、一度も見せていない場面があれば人に伝え、見せるか範囲から外すかを聞く。`/show-prototype` が見送りとして返した指摘（媒体を変える・作り直しになる）は、試作を作り直すか、`ux.md` の未決に残すかを人に聞く。

次の 3 つがそろったら固め終わりとする。

- 人が「これで固める」と言った
- すべての `feedback.md` で状態が「未反映」の行が 0 件
- 手順 2 の場面がすべて一度は見せてある（範囲から外した場面を除く）

### 5. 決定を書き出す

`docs/features/<slug>/ux.md` に次の形で書く。シナリオの表は、実装後の `/demo` のシナリオに写せる粒度で書く（完了条件との対応付けは `/define-feature` が行う）。

```text
# {機能名} の UX の決定

- 媒体: {Web / CLI / API / バッチ / ゲームの画面の流れ}
- 試作: docs/features/<slug>/prototype/
- 指摘一覧: {feedback.md のパス}（反映済み N 件 / 見送り N 件）

## 決定

| # | 画面・場面 | 決めたこと | 出どころ（feedback.md の #） |
|---|-----------|-----------|----------------------------|

## シナリオ

| # | シナリオ | 前提 | 操作 | 見えるもの | 試作のファイル |
|---|---------|------|------|-----------|--------------|

## 未決・見送り

- {指摘と理由}

## 範囲外

- {試作で扱わなかったこと・範囲から外した場面}
```

指摘一覧は媒体ごとに 1 行ずつ書く。試作は固めた時点の写しであり、実装後に更新しない。

### 6. 完了報告

```text
## UX の決定 完了

- UX の決定: docs/features/<slug>/ux.md
- 試作: docs/features/<slug>/prototype/
- 決定 N 件 / シナリオ N 件 / 未決・見送り N 件

次のステップ:
/define-feature {機能名}（ux.md を渡す）
```

人が途中でやめた場合は、試作と `feedback.md` をそのまま残し、同じ機能名で本スキルを呼び直すと再開できることを示して終わる。

## 注意事項

- 試作を見せる・指摘を記録して反映するのは `/show-prototype` の役目であり、本スキルでは行わない
- 要件・受入基準・クリティカル設計は決めない（`/define-feature` の役目）
- 画像・演出は生成しない
- 試作と `ux.md` は機能仕様と一緒にコミットする。本スキルはコミットしない
