# `description`（skills / agents の frontmatter）の基準

`skills/*/SKILL.md` と `agents/*.md` の frontmatter `description` は、他の実行時テキストと性質が違う。

- **常時ロードされる固定費**である。本文（`SKILL.md` 本体・`agents/*.md` 本体）は起動が決まった1件ぶんだけがオンデマンドで読まれるのに対し、`description` は**全件がセッションの最初から載る**。
- **用途が1つに限られる**。読み手が `description` に対して行う判断は**いつこのスキル／エージェントが起動されるべきか**だけである。手順を実行するのは本文を読んだあとであり、`description` では何も実行されない。

本文書はこの面に限った基準（正本）と、起動トリガーの台帳を置く。

## 0. 判定軸は `docs/plugin-path-conventions.md` (h) の下位規定である

判定軸を別の言葉で書き直さない。正本は (h) の1問であり、ここでは逐語で引く:

> **判定軸**: **この文を削ると、次に読むモデルの振る舞いが変わるか。**

`description` 面では、この「振る舞い」が**起動の判定**に特定される。したがって残るのは**起動の判定に効く語**だけであり、それ以外は本文か人間が読む面（設計文書・PR 本文）へ置く。

### (h) の「前向き適用」と矛盾しない理由

(h) は**既存の実行時テキストの一括掃引を要求しない**（出典と規範が同じ文に同居している箇所があり、番号だけを機械的に削ると規範ごと落ちる。加えて実行時テキスト全面の diff が動くとレビューの焦点が失われる）。`description` 面に限って一度の正規化を行うのは、この 3 点が成り立つためである。

1. **有界で列挙可能**（1 面 1 行・全 45 行）であり、diff がレビューできる規模に収まる。
2. **失敗形が 1 つ**（削りすぎて起動されなくなる）に絞られる。`description` に規範は書かれていない——規範は本文にあるため、「規範ごと落とす」という (h) の懸念がこの面には存在しない。
3. その唯一の失敗形を **§5 の台帳で機械照合できる**。

**この扱いを実行時テキストの本文へ広げない。** 本文は上記 3 点をいずれも満たさない。

本文書は `docs/` 配下の設計文書であり、**実行時ファイルから参照しない**（→ (f)）。基準を実行時に届ける必要が生じた場合は、本文書への参照ではなく逐語コピーで届ける（→ (b)・(h)「この規約は『分量を減らせ』ではない」）。

## 1. 構成（3要素に限る）

`description` の値は、次の順で 3 要素に限る。②は必須、③は条件付き。

| 要素 | 内容 | 必須 |
|---|---|---|
| ① | **何をするか**の 1 文 | 必須 |
| ② | **起動トリガー** — `Triggers on: '語', '語', …` の列挙。値の末尾に置く。**②に何を書くかは面で異なる**（skills は利用者の発話、agents はタスクの形。→ §4） | 必須 |
| ③ | **排他条件**（いつ使わないか・何を担わないか）の 1 文。①と②の間に置く | 条件付き（下記） |

**③を置く条件は「誤起動・混同の実績があること」に限る。** 実績とは、(1) 改修前の `description` に既にその文が置かれていた（過去に誤起動・混同へ対処して入った）か、(2) 他の面と**同じトリガー語を共有している**（例: `/impl` の `'このIssueを実装して'` と `/para-impl` の `'Issueを実装して'`）か、のいずれかである。**想像で足さない**——起動されない面を作る。

**①＋③は合わせて 2 文までである。** これは分量の上限ではなく**3 要素への正規化の機械化**である（→ §3・§6）。3 文以上になった `description` は、例外なく手順の要約か内部実装の説明を抱えている。

## 2. 削る判定軸（「削るとモデルの振る舞いが変わるか」の適用）

| 残す | 削る（本文か人間が読む面へ） |
|---|---|
| トリガー語（起動の判定に直接効く語） | **手順の要約**（`ブランチ準備→設計→TDD実装→コミット→E2E→PR` のようなフローの列挙） |
| 排他条件（§1 の条件を満たすもの） | **内部実装の説明**（どの観点軸で分類するか・どの形式の中間成果を経由するか） |
| 他の面との区別に効く語（同じ領域に複数の面がある場合の、入力・起点・出力の違い） | **効能の宣伝**（「人間はコードを読まずにレビューできる」「〜を最大化する」） |
| 安全性の制約（それを外すと壊れる使い方を禁じる文） | **本文へ書けば足りる詳細**（成果物のパス・中間ファイルの形式・引数の綴り〔`argument-hint` の責務〕） |

「自動委譲される」「〜するスキル」「〜する際に使用するエージェント」といった**面の種別そのものの再説明も削る**。読み手は `skills/` `agents/` のどちらを読んでいるかを既に知っている（→ (h)「読み手が既に知っている前提の再説明」）。

## 3. 分量の一律上限は置かない

`CLAUDE.md` に置いている分量基準（200 行）は `description` には当てない。本文はオンデマンドで、分量が読み込み費用にそのまま比例するが、`description` は**常時ロードかつ「選択のための情報」**であり、削りすぎると**起動されなくなる**という非対称な失敗を持つ。したがって目標は文字数の上限ではなく**3 要素への正規化**であり、機械で固定するのは §1 の構造（②の存在と位置・①＋③の文数）だけである。

**改修の前後で実測を報告するときは、文字数とバイト数のどちらで測ったかを必ず明記する。** 日本語の `description` は 1 文字 ≒ 3 バイトであり、単位を書かないと同じ面の測定値が 3 倍ずれて「合わない」と読まれる（Issue #243 の起票時の数値は文字数ではなくバイト数だった）。

## 4. agents も同じ基準（ただし②の語彙は skills と別物）

`agents/*.md` の `description` も常時ロードされる固定費であり、同じ 3 要素に正規化する。**違うのは②に何を書くかである。**

| 面 | ②に書くもの | 理由 |
|---|---|---|
| skills | **利用者の発話**（`'コミットして'`・`'/commit'`） | スキルの起動は利用者の入力が決める。発話そのものが**選択の入力**である |
| agents | **タスクの形**（`'ファイル起点で技術負債の指摘を反証したいとき'`）。委譲元は**例示**として括弧で添える（`（例: /reduce-debt からの委譲）`） | agents は Agent ツールでモデルが**意味で選ぶ**。利用者は「`/reduce-debt からの委譲`」とは言わないため、呼び出し元の名指しは選択の入力と一致しない |

### 呼び出し元の名指しを②にすると、逆に呼ばれなくなる

**列挙は網羅（ホワイトリスト）として読まれやすい。** ②に `'/reduce-debt からの反証委譲'` とだけ書くと、**それ以外の経路では呼ばない**と読める。これは起動を増やすどころか減らす方向の誤りであり、`description` 面の失敗（削りすぎて起動されなくなる）と同じ沈黙した形で起きる。

実際に過小記述になる: `debt-verifier` は `/reduce-debt` 以外にも 3 ファイルから参照され、`finding-verifier` は 9 ファイル（うち委譲元は 3 スキル・4 ファイル、残りは他エージェントからの言及）から参照される。**呼び出し元を数え上げて書き切るのは維持できない**——経路が増えるたびに `description` を追う必要があり、追わなければ②が現実より狭いまま残る。

タスクの形で書けば、経路が増えても②は変わらない。委譲元は**そのタスクが実際に起きる文脈の例**として1〜2件だけ添え、`例:` と明示して網羅ではないことを読み取れるようにする。

### 利用者が直接その言葉で依頼する agents は、利用者語彙のままでよい

`code-reviewer`・`design-reviewer`・`doc-verifier`・`e2e-engineer`・`feature-implementer` の 5 面は、利用者が実際に「コードをレビューして」と言って自動委譲される。この場合**利用者の発話がそのままタスクの形**であり、書き換える必要はない（委譲元の例示も不要——特定の面からの委譲で起動するわけではないため）。

### ②に新しい依頼文言を足さない

依頼文言を増やすと自動委譲の対象そのものが変わる（スキルが担うべき依頼を agents が奪う）。正規化で足すのはタスクの形と委譲元の例示だけであり、**利用者語彙は改修前に持っていたものを保持する**。

## 5. 起動トリガー台帳（回帰の正本）

`description` から語を削る変更は、**起動されなくなるという沈黙した失敗**を作る。台帳は「各面が保持すべき起動トリガー語」の正本であり、`scripts/tests/test-description-conventions.sh` が現物と照合する。

- **起動トリガー列**: その面の `description` の `Triggers on:` トークン集合と**完全一致**する（双方向）。トリガーを増やす変更も減らす変更も、台帳の編集を伴う＝レビューで見える。
- **保持語列**: 改修前の `description` が持っていた語彙のうち、正規化で①へ移った語。`description` のどこかに逐語で在ることだけを見る（**片方向**——台帳外の語が `description` に在ること自体は欠陥ではないため。集合一致で縛るのは起動トリガー列の役目）。

## 6. 機械が検査できる水準の境界

(h) と同じ境界が `description` 面にも当てはまる。**「テストが緑＝基準に沿っている」ではない。**

| 要求 | 機械検査 | 強制する主体 |
|---|---|---|
| ②が在り、値の末尾に置かれていること | **検査できる** | `scripts/tests/test-description-conventions.sh` (D-2) |
| ①＋③が 2 文までであること | **検査できる** | 同 (D-2) |
| スラッシュトリガーが実在する面を指していること | **検査できる** | 同 (D-3) |
| agents の②が**呼び出し元の名指しだけ**で構成されていないこと（委譲元は `（例: …）` の中だけに置かれていること） | **検査できる** | 同 (D-5) |
| 台帳の起動トリガーと現物が一致し、保持語が消えていないこと | **検査できる** | 同 (D-4) |
| ①が「何をするか」であり、手順の要約・内部実装の説明・効能の宣伝でないこと | **検査できない**（「起動の判定に効くか」は文の意味に依存する） | `agents/code-reviewer.md` 観点G（(h) の書き分けとして）／PR レビュー |
| ②のタスクの形が、モデルが実際にその agents を選ぶときの語と合っていること | **検査できない**（選択は意味で起きる。語の網羅性も妥当性も決定的スクリプトでは測れない） | PR レビュー／実運用での観察 |

**語彙ベースの不在検査（「フロー」「最大化」等の禁止語）は採らない。** 理由は (h)「禁止語の不在検査にしない理由」と同じで、正当な用例が構造的に存在する（`/quality-check` の①は `lint・型チェック・テスト` の列挙そのものが「何をするか」である）。
