# `.claude/rules/` の導入可否 — 判断材料（案と推奨）

> **位置づけ**: Issue #242 の判断材料。**どの案を採るかはこの文書では決めていない**（決めるのは人間）。
> 根拠にした実測は `docs/settings-governance.md` §2.1（2026-09-20 / Claude Code 2.1.278 / macOS）にあり、本文書の `R1`〜`R17` はその表の行番号を指す。
> 案が確定したら、`/init-project` の実装変更・冪等マージ・`preflight` への検査追加は別 Issue として起票する（本文書の範囲外）。

## 1. 何の行き先を決めるのか

#237（PR #240、コミット `83a7986`）は、`skills/init-project/templates/CLAUDE.md.template` から次の 4 節を削除した。削除の理由はコミットメッセージに書かれているとおりで、**4 節とも「コードベースから導ける内容」または「一般論」だから**である。

| 削除された節 | 中身（プレースホルダ） | 削除理由（`83a7986` のメッセージ） |
|---|---|---|
| `## プロジェクト概要` | `{PROJECT_DESCRIPTION}` | architecture overview |
| `## 開発原則` | YAGNI / KISS / DRY ＋ `{ADDITIONAL_PRINCIPLES}` | ツール既定と異なる規約ではない一般論 |
| `## 技術スタック` | Frontend / Backend / DB / Test / Infra / Package の表 | dependency list |
| `## ドキュメントマップ` | `{DOCUMENT_MAP}`（「作成予定」の行を含む） | directory layout。「作成予定」の行が未実在パスを常時ロードさせていた |

同じコミットは、節ではないが `### 命名規則` の表も落とし、`### 新規ファイルの置き場` に置き換えている。

Issue #242 の本文は、移設の候補として別のものも挙げている: 「ディレクトリごとに違う規約（テストの置き場、生成コードの扱い）など、`CLAUDE.md` に置くと全セッションの固定費になるが一部分にしか効かないもの」。**これは削除された 4 節とは別の内容である**。§3 で案を読むときは、「4 節の行き先」と「ディレクトリごとの規約の置き場」を分けて考える必要がある。

本リポジトリは、この文書と §2.1 を書くまで `.claude/rules/` に一度も言及していなかった（`grep -rn 'claude/rules' .` が 0 件。2026-09-20、`9725a09` 時点）。

## 2. 実測のうち判断に効くもの

| 実測 | 判断への効き方 |
|---|---|
| `paths` の無い rule は CLAUDE.md と同じく**起動時に毎回読まれる**（R1） | 4 節を `paths` なしの rule へ移すと、#237 が削った固定費が**場所を変えて戻るだけ**になる。文脈の節約になるのは `paths` を付けた rule だけ |
| 4 節はどれもプロジェクト全体にかかる内容で、特定のパスに結び付かない（§1 の表） | 4 節には自然な `paths` が無い。これは実測ではなく節の中身からの読み取り |
| `paths` 付き rule は **Read のときだけ**発火し、新規ファイルの Write と Grep では発火しない（R16・R17） | 「テストの置き場」「新規ファイルの置き場」のように**まだ無いファイルに効かせたい規約**は、`paths` 付き rule に置いても作成の時点では文脈に入らない。既存ファイルを読んでから編集する規約（生成コードを手で直さない、等）には効く |
| trust 未承認・headless・worktree・サブエージェントのいずれでも読まれる（R1・R13・R14） | tracked の `allow` にあった「clone ごとに trust 承認が要る」という障害は rules には無い。`/para-impl` の worktree worker にも届く |
| `./` で始まるパターンは**黙って一致しない**。スラッシュの無いパターンは全階層の basename に一致し、公式ドキュメントの説明と食い違う（R3・R4・R6） | 生成するなら、パターンの書き方を機械で固定しないと「発火しない rule」を量産する。ドキュメントと実測が食い違っている箇所は、版が上がると挙動が変わりうる |
| CLAUDE.md と rules が矛盾したときの勝ち負けは一定しない（R15） | rules は CLAUDE.md を上書きする層として設計できない。再実行時のマージは「同じことを 2 箇所に書かない」を守る必要がある |
| 未対応バージョンでの挙動は**未実測** | 既に scaffold 済みのプロジェクトや古い Claude Code の利用者に対して、「無視されるだけで害は無い」とは**まだ言えない** |

## 3. 案

### 案A: 導入して、削除した 4 節を `.claude/rules/` へ移設する

`/init-project` が `.claude/rules/` を生成し、4 節の内容をそこへ書く。

- **得るもの**: 削った内容に行き先ができる。CLAUDE.md 本体は 200 行未満の目標を保てる。trust 承認なしで全 worker に届く（R1・R13・R14）。
- **失うもの・リスク**:
  - 4 節に自然な `paths` が無いため、`paths` なしで置くことになり、**毎セッションの固定費は #237 の前に戻る**（R1）。#237 が削った理由（コードベースから導ける・一般論）は、置き場を変えても消えない。
  - 無理に `paths` を付ければ固定費は減るが、その場合は「何を読んだときに技術スタックの表が要るのか」を決める必要があり、根拠のある線が引きにくい。
  - 後方互換（再実行時の冪等マージ）と `preflight` の検査を新設する必要がある。未対応バージョンでの挙動が未実測のまま生成物を増やすことになる。
  - 実行者の環境のようにグローバル gitignore が `.claude/*` を除外していると、生成した rules が commit されない（§2.1 の付記）。
- **変種（案A'）**: 4 節は移さず、**Issue #242 が候補に挙げた「ディレクトリごとに違う規約」だけ**を `paths` 付き rule として生成する。こちらは `paths` が自然に決まり、固定費も減る。ただし R16 により、新規ファイルの置き場の規約には効かず、効くのは「既存ファイルを読んでから触る」規約に限られる。案A' は 4 節の行き先の問いには答えない（4 節については案C と同じ扱いになる）。

### 案B: 導入せず、skill 側へ移設する

- **前提の確認**: `/init-project` が生成するのは `CLAUDE.md` と `.claude/settings.json` で、**プロジェクト側の skill は生成していない**。したがって「skill 側」には 2 つの読み方がある。(B-1) harness のスキル（`/impl` 等）が、必要になった時点でコードベースから技術スタックや文書の所在を導く。(B-2) `/init-project` がプロジェクト側に skill を新しく生成する。
- **得るもの**: skill は呼ばれたときだけ読まれるので、固定費がかからない。(B-1) なら生成物は増えず、後方互換の問題も起きない。
- **失うもの・リスク**:
  - 4 節の中身は**手順ではなく事実**（概要・スタック・文書の所在・原則）で、公式ガイドが skill へ移す対象に挙げる「多段手順」に当たらない。
  - (B-1) は、harness のスキルが設計ドキュメントへの到達を探索フォールバックへ寄せた現状（#241、`9725a09`）と実質的に同じ方向で、新たに移設する作業がほとんど残らない。つまり案C との差が小さい。
  - (B-2) は生成物の種類を増やし、案A と同じ後方互換・検査の新設が要る。skill の発火はモデルの判断に依るため、読まれる保証は rules より弱い。
  - skill 側の挙動は本課題では実測していない。

### 案C: 現状維持（移設先を作らない）

- **得るもの**: #237 の判断（4 節はコードベースから導ける・一般論なので削る）と一貫する。生成物・検査・マイグレーションが増えない。未実測の範囲（未対応バージョン、対話セッション）に依存しない。
- **失うもの・リスク**:
  - 「ディレクトリごとに違う規約」を全セッションの固定費なしに置く場所が、引き続き無い。利用者が自分で `.claude/rules/` を書くことは妨げないが、harness は書き方の落とし穴（`./` は一致しない、Write では発火しない）を案内しない。
  - `{ADDITIONAL_PRINCIPLES}` のように、利用者が答えた**プロジェクト固有の原則**は、一般論の YAGNI / KISS / DRY と一緒に落ちている。これがコードベースから導けない内容だった場合、行き先が無い（ただし現行テンプレートの `## 開発規約` 配下に書く余地はある）。

## 4. 推奨

**4 節の行き先としては案C を推奨する。** あわせて、Issue #242 が挙げた「ディレクトリごとの規約」を扱うかどうかは、4 節の問いから切り離して**案A' として別に判断する**ことを勧める。

根拠:

1. **4 節を rules へ移しても節約にならない**（R1）。`paths` なしの rule は CLAUDE.md と同じく毎回読まれる。4 節には自然な `paths` が無いので、案A は #237 が削った固定費を別のファイルへ戻す結果になる。
2. **4 節が削られた理由は「置き場が悪い」ではなく「書く必要が無い」**だった（`83a7986`）。公式ガイドが skill / path-scoped rule への移設を勧めているのは「多段手順」と「一部分にしか効かない指示」で、4 節はどちらでもない。行き先が宙に浮いているのではなく、行き先が要らない内容だった、と読むほうが #237 と整合する。
3. **案A' は機構としては成立する**が、決める前に知っておくべき制約が実測で出た。trust なしで全 worker に届く（R1・R13・R14）一方、新規ファイルの作成には効かず（R16）、`./` 付きのパターンは黙って死に（R3・R4）、`*.md` の意味は公式ドキュメントと食い違う（R6）。生成するなら、パターンの書式を機械で固定する検査が前提になる。
4. **未対応バージョンでの挙動が未実測**である。生成物を増やす案（A・A'・B-2）は、この空白を埋めてから進めるのが安全で、案C はこの空白に依存しない。

推奨の確度について: 1 は実測に直接基づく。2 はコミットメッセージと公式ガイドの読み取りで、実測ではない。3 の制約は実測だが、「それでも導入する価値があるか」は、利用者のプロジェクトにディレクトリごとの規約がどれだけあるかに依り、本課題では調べていない。

## 5. 決めてほしいこと

1. 4 節の行き先: **案A / 案B / 案C のどれを採るか**。
2. 案C または案B を採る場合、**案A'（ディレクトリごとの規約だけを `paths` 付き rule で生成する）を別 Issue として検討するか**。検討するなら、先に未対応バージョンでの挙動と、Edit・Glob での発火を測る必要がある（§2.1「言えない」）。
3. `{ADDITIONAL_PRINCIPLES}`（利用者が答えたプロジェクト固有の原則）が一般論と一緒に落ちている点を、別に扱うか。

## 6. 置いた仮定

- 「削除 4 節」は `83a7986` のコミットメッセージが列挙する 4 つの `##` 節を指し、`### 命名規則` の表は含めない、と解釈した。
- 案B の「skill 側」は Issue にも承認済みタスク案にも定義が無いため、(B-1)(B-2) の両方を書いた。
- 案A' は承認済みの 3 案には無い。Issue #242 の本文が挙げる候補と 4 節が別物だったため、案A の変種として併記した。3 案の枠を変える意図は無く、採否は判断に委ねる。
- 実測記録は `docs/settings-governance.md` の §2 直下に §2.1 として追記した（既存の §2 の行と §3 以降の番号は変えていない）。案と推奨は主題が許可設定から外れるため、本文書に分けた。
