# ADR 0002: GDD（保証駆動開発）を不採用とし、計装のみ回収する

- **ステータス**: Accepted
- **日付**: 2026-08-21
- **関連**: #152（導入検討）・#159（P4 ドッグフーディング実測・採否決定コメント）・#185（粒度規約）・#186/#187/#188（凍結に伴いクローズ予定）

## 背景

GDD は「docs（機能仕様）がコードとドリフトし、嘘をついても検出されない」という SDD の弱点への回答として設計された（#152）。保証台帳を正とし、テスト引用の索引整合を機械検査し、意味の正しさを裁可（人間）で担保する。

P4 ドッグフーディング（#159）で移行・要件化・実装の全フェーズを実プロジェクト（ai-boss・テスト 1365 件）で 1 周し、決定時点で次が実測されていた:

- **決定的ゲート（`guarantee-index-check`）は意味的誤りを 0/77 件しか検出しない**。誤りの検出はすべて LLM＋人間の労働（drift 監査 20・AI レビュー 8 巡で 22・観点別掃引 35）
- bootstrap 抽出の誤り率 26%（172 保証中 77 件を修正）。台帳が正である以上、誤りを 0 に磨く義務が生じる
- 検出価値は実在した: 実装欠陥 7 件（通知の無音喪失・API キー検証欠落等）・GAP 34 件・SDD 仕様書の嘘（FR-06）の露見
- 定常コスト: 要件化 40〜70 分/機能＋維持保証の逐語転記（台帳サイズに比例）＋裁可往復＋文書配送。転記・出力解析・配送・モード判定という決定的に書ける処理がモデル実行になっており、確率的ミスのコストを払っていた
- 全 3 フェーズで「改訂する保証」カテゴリの不在が衝突を起こし、非規定の回避を要した

## 決定

**GDD をレジーム（台帳を正とする開発フロー）としては不採用とする。**オプションとしても提供せず、既存の GDD 機構（台帳正・裁可ゲート・保証節・ID 体系 `G-{n}-{m}`）は**凍結**する——削除はせず experimental を明示し、追加投資しない。

**計装は回収する**:

- `guarantee-audit`（bootstrap/drift）は**台帳非依存の「公開面×テストカバレッジ診断ツール」**へ再位置づける。出力は保証台帳ではなく Issue 群とし、診断精度はトリアージ前提とする（ラスト 1 マイルの磨き込み義務を発生させない）
- 保証の粒度規律（#185: 1 主張=1 検証・原子化の停止条件）は SDD の受入基準の書き方ガイドとして残す
- `quality-check-runner` の false pass（引数なし実行が全ゲート skip で pass を返す）は GDD と無関係の安全網の穴として修正する

**既定の開発フローは SDD＋コード正（テスト正）とする。**docs は機能追加時の補助資料（短命な作業文書）であり、正しさを担保しない（非権威）。ドリフトの検出は定期のテスト監査（回収した計装）が担う。DDD の併用は妨げない。

スコープ外: ai-boss 等の利用先プロジェクトの個別の後始末（進行中の作業の完走・台帳の退役手順）は各プロジェクトの判断に委ねる。

## 検討した代替案

| 案 | 内容 | 却下した理由 |
|---|---|---|
| GDD を全面採用 | 台帳レジームを既定フローにする | 意味検証の労働が恒常コストとして残り（決定的ゲートでは 0/77 件）、価値の回収は「仕様書が既に嘘をついている」プロジェクトに偏る。全プロジェクト既定化を支持する実測が無い |
| GDD-lite（オプションとして採用し改善を続ける） | 摩擦（改訂カテゴリ・転記・出力肥大等）を潰しながら opt-in で提供 | 価値の大半は監査という行為から出ており、台帳レジームからではない。レジームを残す＝配管（2 日で 5 PR 分の修正・未修正 6 件・構造未決 3 Issue）の保守を恒久に引き受けることになり、ラスト 1 マイルの磨き込み義務（台帳の権威性の帰結）も消えない |
| SDD＋コード正＋計装回収（採用案） | docs を非権威に落とし、監査だけ道具として残す | — |

## 帰結

- **利点**: FR-06 型の「docs の嘘」は docs の非権威化で無害化される（嘘を検出する労働自体が不要になる）。GAP 検出（コード正だけでは原理的に得られない負の在庫）は診断ツールとして残る。レジーム維持費（転記・裁可往復・ID ライフサイクル・意味検証の全数義務）が消える
- **コスト・制約**: 意図した約束の恒常的な明文化は失われる——テストが約束の唯一の執行可能な表現になり、テストの無い振る舞いは「コードがやっている何か」でしかない（この盲点を定期診断で補う設計）。凍結した GDD 機構はコードベースに残り、読み手に experimental である旨の明示が必要
- **将来の見直し条件**: 意味検証を決定的に（または大幅に安く）行える手段が実用化された場合。もしくは「docs を正としなければならない」外部制約（規制・監査要件等)を持つプロジェクトが現れた場合
