# ADR 0004: `/self-review` の収束条件を severity しきい値で切り、残指摘を必ず下流へ渡す

- **ステータス**: Accepted
- **日付**: 2026-08-26
- **関連**: Issue #204・Issue #107（`/self-review` の Task 委譲化）・Issue #130（単一懐疑者への統一）

## 背景

`/self-review` の収束条件は「指摘がゼロになるまで（`findings.length === 0`）」だった。指摘が残ったまま上限3周に達すると `converged: false` を返し、残指摘は `residualFindings` として呼び出し元に渡る、という設計である。

Issue #204 は、この条件が**成果物の性質によっては構造的に満たされない**ことを指摘した。起票者が別リポジトリ（ai-boss）で観測した内容は次のとおり:

| 課題 | 成果物の性質 | ラウンド | 初回の指摘数 |
|---|---|---|---|
| ai-boss#219 | 実装＋テスト | 3 で収束 | — |
| ai-boss#172 | 実装3箇所＋テスト | 3 周上限に達し `converged: false` | 12 |
| ai-boss#196 | テストのみ1ファイル | 4 / 3 / 3 | 16 / 約8 / 10 |

`high` severity は全課題・全ラウンドで 0 件で、残っていたのは「positive control の重複・恒真テスト・DRY 違反・コメント精度・一時ファイルの残留」といった `low` の指摘だった。

> **未検証**: 上記の数値は Issue #204 起票者による別リポジトリでの報告であり、**本リポジトリでは再現を確認していない**。本 ADR はこれを設計の動機として扱うが、実測済みの事実としては扱わない。以下の「分岐の説明」も同様に、観測を説明する仮説である。

**分岐の説明（仮説）**: 実装コードのレビューには外部のオラクル（動くか・テストが通るか・変異させたとき狙ったテストが落ちるか）がある。バグを直せば、そのバグに関する指摘は二度と出ない——**修正がレビュー面を減らす**。テストコード・ドキュメント・リファクタ・命名にはこの基準が無く、しかも修正が新しい批評面を生む（コメントを直せば新しい文言が批評対象になり、ヘルパを抽出すればその抽出単位が批評対象になる）。**減った分だけ増える**ので、指摘がゼロになる状態には到達しない。

分岐は「タスクがあいまいかどうか」ではなく、**修正がレビュー面を減らすのか、同じ速さで生むのか**にある。

## 決定

**収束を「指摘ゼロ」ではなく「修正しきい値以上の残指摘がゼロ」で判定し、しきい値未満の指摘は自動修正せず、`converged` の値に関わらず全件を下流へ渡す。**

1. **severity の順序と2つのしきい値を、`skills/self-review/SKILL.md` の1箇所（`convergence-canon` ブロック）だけで定義する。** 順序は `high` > `medium` > `low`。**検証しきい値** = `high`（Step 3 の懐疑的検証にかかる範囲。従来どおりで変更しない）、**修正しきい値** = `medium` 以上（Step 4 の自動修正の対象・`converged` を左右する範囲）。Step 3 以降は severity の値を再列挙せず、この語で参照する。
2. **未知の severity は `high` として扱う（fail-closed）。** 3値以外の値・欠落・読み取れない応答を軽い側へ落とすと、修正もされず収束も妨げないまま消える。これにより「許容値のリスト」と「しきい値未満のリスト」という第2のリストを作らずに済む（2つのリストは必ず同期がずれる）。
3. **修正しきい値未満（`low`）の指摘は自動修正しない。** `residualFindings` に `reason: below_fix_threshold` で計上し、`converged` を `false` にしない。修正の要否は呼び出し元が決める。
4. **`converged: true` は「残指摘が無い」を意味しない**という帰結を明示し、**残指摘の受け渡しを `converged` で分岐させない**。`residualFindings` が空でなければ、`converged` の値に関わらず全件を報告・転記する（`/self-review` Step 6/7 → `feature-implementer` の返却内容 → `para-impl` の PR 本文 / `ticket-worker` の返却内容）。
5. **収束判定を真理値表として書く。** 入力は3つ（`/quality-check` の `fail`／非機械可読・修正しきい値以上の残指摘・修正しきい値未満の残指摘）で、表は全8組合せを重複なく網羅する。`converged` が散文と表の2箇所でずれることを機械検査できる形にするため。
6. **`residualFindings` を1本の配列のまま維持する。** しきい値以上／未満で別配列に分けない（`severity` で判別でき、2本の配列は同期がずれる）。
7. **ラウンド上限（3周）は成果物の性質で変えない。** オラクルの有無を自動判定させると、その判定自体が誤る。一律上限＋severity 収束で足りる。
8. **終了条件から「指摘が0件」を独立条件として外す。** `toFix` が空になる条件がこれを包含する（指摘ゼロの周・しきい値未満のみの周・しきい値以上が全て `uncertain` の周はいずれも `toFix` が空）。2つの条件を並べると、片方だけが更新されて食い違う。

## 掃引の範囲（変えた箇所・変えない箇所）

規則の横展開は、適用範囲の例外を先に確定しないと別種の欠陥を作る。今回の対象は「`/self-review` の収束条件と、その結果を消費する経路」に限る。

**変えた箇所**:

| ファイル | 変更 |
|---|---|
| `skills/self-review/SKILL.md` | 正本ブロックの新設（Step 2）・`toVerify`/`toFix` の語彙参照化（Step 3/4）・終了条件の統合（Step 4）・`residualFindings`/`converged` の再定義（Step 5）・報告を `converged` 非依存に（Step 6/7） |
| `agents/feature-implementer.md` | 5-2 で残指摘の受け取りを `converged` 非依存に。返却内容を「残指摘の有無」から `residualFindings` 全件へ。`failure` 時の返却にも追加 |
| `skills/para-impl/SKILL.md` | Phase 4-5 の受け取り項目に残指摘全件。Phase 8 で PR 本文への転記を必須化 |
| `agents/ticket-worker.md` | 返却内容に `converged` と残指摘全件 |

**変えない箇所（意図的な例外）**:

| ファイル | 変えない理由 |
|---|---|
| `agents/code-reviewer.md`・`agents/design-reviewer.md` | レビュアーは `severity` を**付与する**だけで、しきい値判定は `/self-review` の責務。しきい値をレビュアー側に書くと2箇所目のリストになる |
| `agents/finding-verifier.md` | 懐疑者は `verdict` を返すだけで、どの指摘が回ってくるかは呼び出し元が決める。検証しきい値（`high`）自体も変えていない |
| `skills/create-ticket/references/decompose-mode.md` の `converged` | タスク分解の網羅性・依存グラフの収束であり、レビュー指摘の収束とは別概念 |
| `skills/reduce-debt/SKILL.md` の `needs_human_judgment` | 負債検出の多数決結果であり、別スキルの別概念 |
| `skills/codex-review/SKILL.md` | 「Codex の指摘0件は `/self-review` の収束を意味しない」という文は、収束条件の定義に依存しない |
| `skills/pr-merge/SKILL.md`・`skills/promote-verify/SKILL.md` | 単一懐疑者設計の先例として `/self-review` を参照しているだけで、収束条件を消費していない |
| `docs/adr/archive-2026-08-01-*` | 歴史記録。当時の設計を書き換えない |

## 検討した代替案

| 案 | 内容 | 却下した理由 |
|---|---|---|
| 成果物の性質でラウンド上限を変える | 「オラクルの有無」を判定して、無い側は1周で打ち切る | 判定そのものが誤る（テストコードを含む実装課題はどちらにも見える）。誤った側に倒れたとき、実装のバグを1周で見逃す |
| `low` も従来どおり自動修正し、上限だけ下げる | 変更を最小にする | 上限を下げても「修正が新しい批評面を生む」性質は変わらず、打ち切り時点の残指摘の中身が変わるだけ。かつ実装課題のレビュー深度を巻き添えで削る |
| `residualFindings` をしきい値以上／未満で2本の配列に分ける | 下流が `converged` を見ずに済み、フィルタが不要になる | 2本の配列は同期がずれる。`severity` を持たせてあるので下流は1本のまま判別できる |
| `converged` を3値（`true` / `partial` / `false`）にする | 「しきい値未満だけ残っている」を型で表せる | 既存の `converged: false` を優先判定に使っている経路（`feature-implementer` 5-2 の `quality-check` 失敗）が `partial` の扱いを追加で決める必要が出る。真偽値のまま「`true` でも残指摘は載る」を規約で固定するほうが、変更点が少なく退行しにくい |
| 未知の severity を `low` として扱う | 壊れた応答でループが止まらなくなるのを避ける | 偽収束になる。壊れた応答が自動修正もされず収束も妨げないまま消えるのは、Issue #91 で実機確認された「terminal 失敗を指摘ゼロとして集計し `converged: true` を返す」と同じ失敗形 |
| 収束条件を `docs/` に置き、SKILL からは参照させる | 実行時テキストを短くできる | 収束条件はモデルの停止判断そのもの＝行動を変える文であり、参照ファイルへ出すと最も必要な文脈（headless 委譲）で届かない（`docs/plugin-path-conventions.md` (b)(h)） |

## 帰結

- **利点**: 外部オラクルを持たない成果物（テスト・docs・リファクタ・命名）で、上限まで回してから `converged: false` を返す代わりに、`low` を引き渡して早く止まる。`converged` が「重い指摘が残っていないか」だけを表すようになり、意味が絞られる。残指摘が PR 本文まで機械的に届くため、下流（親セッション・人間）が変異確認などで担保を測り直さずに引き取れる。
- **コスト・制約**: `converged: true` の意味が変わった（「残指摘なし」ではない）。`converged` だけを見ていた消費側は、残指摘を落とす。今回の掃引で本リポジトリ内の消費側3経路は更新したが、**このプラグインを使う外部プロジェクト側の記述までは掃引していない**。
- **機械検査の境界**: `scripts/tests/test-self-review-convergence.sh` が固定するのは**規約の構造**（正本ブロックが1つ在ること・severity 語彙が正本の外に無いこと・真理値表が全組合せを網羅し参照実装と一致すること・旧条件の語彙が実行時テキストに残っていないこと・消費側3経路が残指摘の全件転記を規定していること）であり、**実行時にモデルがこの収束条件を守るかどうかは検査できない**（LLM の実行時の振る舞いに依存する）。
- **将来の見直し条件**: 修正しきい値が `medium` では粗すぎる／細かすぎるという実測が本リポジトリで得られたとき。`low` の残指摘が PR 本文で無視され続けることが観測されたとき（渡し先を Issue 起票などへ変える判断が要る）。
