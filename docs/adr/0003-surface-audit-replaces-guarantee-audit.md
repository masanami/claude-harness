# ADR 0003: 監査を `/surface-audit`（公開面 × テスト担保の診断）として作り直す

- **ステータス**: Accepted
- **日付**: 2026-08-22
- **関連**: ADR 0002（GDD 不採用と、その改訂2「凍結ではなく削除」）・Issue #194・Issue #159（実測）

## 背景

ADR 0002 は GDD をレジームとして不採用とし、**計装だけを回収する**と決めた。回収対象の第一が監査（旧 `/guarantee-audit`）である。同 ADR の改訂2（2026-08-22・人間決定）で「凍結して残す」という手段が撤回され、**GDD 固有の資産は削除**することになった（凍結物が残ると利用者が現役の規約と誤読するため。後方互換は不要）。

決定時点で真だったこと:

- 検出価値（実装欠陥 7 件・GAP 34 件）は**監査という行為**から出ており、保証台帳というレジームからではない（Issue #159 の実測）。**診断精度は 74%** で、残りは誤検出・判断保留
- 旧 `/guarantee-audit` は台帳を入力または出力に持つ2モード（`bootstrap`＝台帳ドラフト生成 / `drift`＝台帳と実態の乖離検出）で構成されていた。**GAP 検出（テスト未担保の公開面の洗い出し）は `bootstrap` の一工程**にすぎず、その出力先は台帳ドラフトだった
- 旧 `guarantee-auditor` エージェントは `extract`（テストから振る舞いを抽出。台帳非依存）と `verify`（台帳の約束とテストの整合判定。台帳必須）の2モードを持っていた
- 台帳が無くなると、`guarantee-index-check`（台帳の索引整合チェック）と `detect-dev-phase`（SDD期/GDD期 の宣言判定）は**呼び出し元を失う**
- 定期実行の呼び出し元は中立形式の監査結果だけを消費し、接続ツールのネイティブ出力は解釈しない。変換は呼び出し元の設定が持つ（**この事実は claude-flywheel 側のドキュメント由来であり、本リポジトリのコードからは検証できない**）

## 決定

**監査を `/surface-audit`（公開面 × テスト担保の診断）として作り直し、台帳に関わる経路をすべて削除する。**

1. **スキルを改名する**: `guarantee-audit` → **`surface-audit`**、`guarantee-auditor` → **`surface-auditor`**。台帳（guarantee）が存在しない以上、その名を冠したスキルは利用者に無い概念を想起させる。改名の障害だった「凍結ドキュメント群が旧名を名指ししている」状態は、GDD 削除で消えた。
2. **単一の手順に一本化する**: `bootstrap`・`drift`・`verify` を削除し、モード選択を廃止する。**手順は `SKILL.md` 1本に収め、`references/` を持たない**（参照ファイルの配送は失敗が沈黙する経路であり、常に必要な手順を配送に乗せる理由が無い）。引数も取らない。
3. **診断は常に全量で行う**（差分範囲の指定を受け付けない）。差分に絞ると、差分に現れない既存の未担保公開面——検出したい対象そのもの——を落とす。
4. **出力契約**: 成果物は最終応答に出す**機械可読 JSON ＋ 人間向けサマリー**だけとし、**ファイルを書かず、Issue も起票しない**。維持される成果物を作らないことが、ADR 0002 が畳んだ「文書を正として維持し続けるコスト」を再発させないための線である。起票の粒度と要否は呼び出し元が決める（推奨はカテゴリ単位で1 Issue）。
5. **精度はトリアージ前提**（実測 74%）。候補を 100% へ磨き込む義務を負わない。**ただしこれは判定の当たり外れの話であり、検査していない範囲を検査済みとして出してよいことは意味しない**——工程ごとの `status`（`analyzed` / `partial` / `not_analyzed`）で必ず開示し、**未解析の工程が産む値は `0` ではなく `null`** とする。
6. **不完全さの誤差の向きを工程ごとに区別して開示する**。GAP は否定の判定であるため、テスト列挙・抽出の欠落は**誤検出（過剰）**を、公開面カテゴリの列挙漏れは**検出漏れ（過少）**を生む。「下限」と一括りにしない。突き合わせの基準が成立しない場合（抽出が全件失敗・公開面が1件も列挙できない）は `not_analyzed` とし、候補も件数も出さない。
7. **`surface-auditor` は `extract` 相当の単一責務**とし、`assertion`（`asserted` / `vacuous`）を返す。skip / todo / アサーション不在 / 常に真の比較を `vacuous` とし、**対応する振る舞いがすべて `vacuous` の公開面も GAP** として扱う（テスト参照の存在だけで担保済みと判定すると、skip されたテストが「担保あり」になる）。判断が付かない場合は `asserted` に倒す（誤った `vacuous` は誤報になるため）。
8. **`guarantee-index-check` と `detect-dev-phase` を、スクリプト・仕様・テストごと削除する**。前者は台帳の索引整合を検査するもので、台帳が無ければ検査対象が存在しない。後者は GDD期/SDD期 の宣言を読むもので、宣言そのものが廃止された。**`list-test-files` は残す**（本スキルの入力であり、台帳とは独立）。
9. **`skills/` と `agents/` には、モデルの行動を変える文だけを書く**。用語の言い換え・課題番号・出典・経緯・実測値は書かない（実行のたびに読まれる面であり、行動を変えない記述はコンテキストを食い判断のノイズになる）。理由と経緯は `docs/`・`scripts/specs/`・スクリプト内コメント・PR 本文に置く。**本 ADR がその置き場である。**

スコープ外: `promotion-decision.sh` が使う保証 ID 書式の定数（`lib/common.sh`）の処遇。

## 検討した代替案

| 案 | 内容 | 却下した理由 |
|---|---|---|
| 名前を据え置く（`guarantee-audit` のまま） | 改名によるスラッシュコマンド・allowlist の破壊を避ける | 台帳が1つも残らないため、名前が指す対象が存在しない。**利用者の混乱を避けることが今回の決定の動機**（ADR 0002 改訂2）であり、名前はその混乱の最大の発生源になる |
| `drift` を互換のために残す | 台帳を持つ既存プロジェクトが乖離検出を続けられる | 後方互換は不要と決まった（GDD 導入プロジェクトは少なく、SDD へ戻せば足りる）。残せば台帳・索引チェック・フェーズ判定の一式を保守し続けることになる |
| 手順を `references/` に置いたままにする | SKILL.md を小さく保つ | モードが1つになり、手順は**常に必要**になった。配送を挟むと「読めないまま完走する」失敗経路が残るだけで、削減できるコンテキストが無い |
| 診断レポートをファイルへ書き出す | 履歴を追える | 維持される文書が再び増える（ADR 0002 が畳んだコストの再発）。呼び出し元は最終応答の機械可読部を消費するため不要 |
| GAP ごとに Issue を起票する | 「出力は Issue 群」を文字どおり実装する | 起票は不可逆な外部作用であり、監査と修正の分離を壊す。実測（GAP 34 件）では 1 GAP = 1 Issue が全体像を消す |
| 上流が1件でも失敗したら GAP を出さない | 誤検出を完全に避ける | 出力先が台帳ではなくトリアージ対象の候補になり、誤検出の後始末コストが下がった。1ファイルの読み取り失敗で定期診断が毎回沈黙するほうが害が大きい。代わりに**誤差の向きと盲点の一覧を必ず開示する**（決定 6） |
| `guarantee-index-check` を残す | 将来また台帳を使う可能性 | 呼び出し元が1つも無いスクリプト・仕様・テスト（合計 100KB 超）を保守し続けることになり、「凍結物が利用者を混乱させる」という今回の決定と正面から衝突する。必要になれば git 履歴から復元できる |

## 帰結

- **利点**: 台帳の概念を知らなくても使える診断になった。維持される成果物（台帳・レポートファイル）が増えない。「テストはあるが担保していない」公開面（skip・アサーション不在）を検出できる。実行時ファイルから GDD の語彙が消え、読み手が現役の規約とだけ向き合える
- **コスト・制約**: 診断は毎回ゼロから走る（前回結果との差分を取らない）。GAP 候補はトリアージが必要。公開面の機械列挙は Glob/Grep に依存し、`ui` のように多くのプロジェクトで `not_analyzed` になるカテゴリが残る。台帳を持つ既存プロジェクトは乖離検出の手段を失う（後方互換は不要という決定の帰結）
- **定期実行との結合**: 呼び出し元が必要とする3点（工程ごとの解析状態 / 検出件数 / 要人間判定の有無）を `steps.*.status`・`counts`・`human_review_required` として機械可読に出す。変換は呼び出し元の責務であり、本スキルは変換先の形式を知らない。**この結合が成立することは claude-flywheel 側のドキュメントに基づく前提であり、本リポジトリのコードでは検証していない**
- **将来の見直し条件**: 公開面の列挙を決定的スクリプトへ移せる見込みが立ったとき（誤差の向きの管理が単純になる）。診断結果の履歴が必要になったとき（出力契約の再検討）
