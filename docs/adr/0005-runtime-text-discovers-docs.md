# ADR 0005: 実行時テキストは `CLAUDE.md` の任意節に単独依存せず、探索へフォールバックする

- **ステータス**: Accepted
- **日付**: 2026-09-20
- **関連**: Issue #241（本 ADR の宣言元）, #237 / #239 / PR #240（`CLAUDE.md.template` の棚卸し）

## 背景

PR #240（Issue #237 の棚卸し）で、`/init-project` が生成する `CLAUDE.md` から「ドキュメントマップ」「開発原則」「技術スタック」「ディレクトリ構成」の各節が削除された。コードベースから導ける内容、および検証できない一般論を実行時に常時ロードさせないための決定であり、その判断自体は妥当である。

一方、`skills/` `agents/` の実行時テキストには「`CLAUDE.md` のドキュメントマップから設計書を読む」「`CLAUDE.md` を読み、開発原則・技術スタック・ディレクトリ構成を把握する」と書かれた箇所が残っていた（実測 10 ファイルが `ドキュメントマップ` に、12 ファイルが `開発原則` に言及）。**新規生成物ではこれらの節が存在しないため、指示された入口が1つも無い状態になる。**

この破れ方は沈黙する。「節が読めなかった」と「設計ドキュメントが存在しない」はモデルから区別できず、突合せを丸ごと飛ばした結果が `確認済み` として返る。生成物はテンプレート追従を持たないため、旧世代（節を持つプロジェクト）と新世代が同時に存在し続ける点も条件を複雑にする。

## 決定

**実行時テキストは `CLAUDE.md` の任意節を唯一の入口にしない。「節が在れば使い、無ければ探索する」の順で書く。**

1. **設計ドキュメントへの到達**は、節ではなく探索が担う。**探索先のディレクトリも形で持つ** — `docs/` は典型だが名前は問わず（`doc/` `documentation/` `spec/` `rfc/` 等があり、ここで新しい列挙を作れば同じ穴が一段上に開く）、無ければリポジトリ直下を見る。そのディレクトリの `*.md` を**全件列挙**し、パス（ディレクトリ名とファイル名）から**その文書が何を述べているか**で選ぶ。配下に `adr/`（設計判断記録）・`features/`（機能仕様）があれば併せて読む。
2. **探索の判定は閉じたキーワード列挙で持たない。** ファイル名のキーワード一致は**構造的に取りこぼす**。実測（2026-09-20・本ハーネスが統治する4リポジトリ、`docs/adr/` `docs/features/` と vendor を除く `docs/**/*.md` 27 件）では、`architecture` / `system-design` / `domain-model` / `erd` / `schema` / `database` / `api-spec` / `openapi` に一致したのは **3 件**（`architecture.md` のみ）で、`requirements.md`（要件定義そのもの）・`settings-governance.md`（権限設計の正本）・`challenge-ledger-format.md`（台帳フォーマット契約の正本）・`branching-strategy.md` などが落ちた。`doc-verifier` の責務は要件定義との整合確認なのに、要件定義に到達できない。
   - **失敗形が非対称**である: 取りこぼしは沈黙し（読めなかったことは「無い」と区別できない）、余分に読む費用はトークンだけ。**リコール優先に倒す。**
   - `docs/**/*.md` は**既に全件列挙している**ため、キーワードは候補を**減らす方向にしか働かない**。判断材料は既に手元にある。
   - **キーワード列挙は実行時テキストに置かない**（この ADR に残す）。「網羅ではない例示」として残す案も採らない——列挙が在ると「一致しないことは除外の理由にならない」「実測ではこれだけ落ちる」という**打ち消しの文がもう一往復ぶん必要になり**、判定基準が「何を述べているか」なら結局使われない。**列挙を消すと、それを打ち消すための文もまとめて消える。**
   - 判断材料は**パス全体**（ディレクトリ名とファイル名の両方）。`docs/design/overview.md` はファイル名だけを見ると手がかりが無い。
   - 件数が多すぎて全件を判断できない場合は、**各ファイル先頭の見出し**で絞る（キーワードではなく、そこでも内容で判断する）。
   - これは同じハーネスが既に採っている規律と同型である（`skills/init-project/scripts/general-exec-allow.json`「載せる基準は列挙ではなく形である」／PR #224「判定の基準は列挙ではなく『〜か』という形で持つ」）。
3. **技術スタック・ディレクトリ構成**は `CLAUDE.md` に書かれないのが既定と明記し、マニフェストと実ディレクトリから得る。**記載が無いことを理由に停止しない。**
4. **開発原則**は上の 3 と束ねない。**導出先が実体に従って分かれる** — マニフェストと実ディレクトリは技術スタック・ディレクトリ構成の実体だが、開発原則の実体ではない（`package.json` に設計原則は書かれていない）。意図的な設計判断の正本は `docs/adr/` であり、無ければ既存コードの実装パターンから読み取る。**束ねると、導ける 2 項目に引きずられて導けない 1 項目が誤った導出先を与えられる。**
5. **「節が無い」を「対象が無い」と読み替えることを明示的に禁じる。** 禁止文を書かないと、到達不能が「不在」として成功報告に化ける（この読み替えこそが沈黙する失敗の本体であり、禁止文は行動を変えるため実行時テキストに残す側に落ちる → `docs/plugin-path-conventions.md` (h)）。
6. **ADR 置き場の解決**も同じ順で行う: `CLAUDE.md` の記載 → `docs/` 配下の `adr` / `decisions` / `decision-records` の探索 → 既定 `docs/adr/`。記載の不在は別パスの証拠でも、停止の理由でもない。
7. **旧世代の生成物を切り捨てない。** フォールバックは「節が在ればそれを使う」を保ったうえでの**追加**であり、置換ではない。`create-adr` のドキュメントマップ追記も、節を持つプロジェクトに対しては従来どおり動く。
8. **厚みは役割に応じて分ける。全ファイルに同じ手順を配らない。** 設計ドキュメントを実際に探して読む消費ステップを持つファイル（`design-reviewer` Step 1 / `doc-verifier` Step 1 / `feature-implementer` Step a-3 / `define-feature` 手順1）だけが探索手順を持つ。持たないファイル（`code-reviewer` は Step 1 が native の方法論、観点 A〜G が `CLAUDE.md` と差分起点で、設計ドキュメントを読むステップが無い）は**読み替え禁止のガードと辿り方の一文だけ**にする。使わない手順を配ると、読まれるたびに費用が出て肝心の指示を薄める（→ `docs/plugin-path-conventions.md` (h)）。同じ扱いを開発原則でも採っている（検証者系5ファイルは軽量な1文）。


### `scripts/analyze-project.sh` の `DESIGN_DOC_PATTERNS` とは揃えない

**意図的に揃えない。** 照合セマンティクスも最適化する方向も違う:

| | 実行時テキスト | `scripts/analyze-project.sh` |
|---|---|---|
| 判定者 | エージェント（意味を読める） | `find -iname` の**前方一致**（`arch.md` は `architecture*` に不一致） |
| 区切り | — | アンダースコア `system_design*` |
| 最適化 | **リコール**（取りこぼしが沈黙するため） | **精度**（`schema.ts` 等の実装ファイルを「整備済み」に数えないため。同スクリプトのコメントが明記） |
| 用途 | 読むべき文書を選ぶ | `/init-project` の9軸判定に1回だけ食わせる前処理 |

スクリプトは「設計ドキュメントが整備されているか」を決定的に判定する前処理であり、偽陽性を避ける必要がある。実行時テキストは「何を読むか」をエージェントが判断する手順であり、偽陰性のほうが高くつく。**同じ列挙を共有すると、精度側の制約がリコール側へ漏れる。**

規約の本文は、共通の参照先へ集約せず**各実行時ファイルへインラインで書き切る**（集約すると headless 委譲で1バイトも届かない → `docs/plugin-path-conventions.md` (b)(f)）。

## 検討した代替案

| 案 | 不採用の理由 |
|---|---|
| **`CLAUDE.md.template` にドキュメントマップ節を復活させる** | #237 の棚卸しを巻き戻す。「作成予定」の行が未実在パスを常時ロードさせる問題が再発し、`docs/` を走査すれば得られる情報を人手で二重管理することになる |
| **`analyze-project.sh` の結果を実行時に参照させる** | 同スクリプトは `/init-project` の初期化時に1回走る設計で、レビュー・実装の各エージェントが毎回起動する前提になっていない。探索そのものは Glob 数回で足りる |
| **共通の参照ファイル（`skills/_shared/`）へ集約し各所は1行参照** | 参照先は headless では既定で読めず、規約が最も必要な文脈で届かなくなる（実測 → (b)）。逐語コピーは冗長に見えて到達性の荷重を負っている |
| **「節が無ければスキップ」で degrade させる（従来の暗黙の挙動）** | スキップが既定経路になる。突合せを飛ばした結果が成功として返るため、検出されない |

## 帰結

- 新規生成物（節なし）・旧世代（節あり）の双方で、設計ドキュメントへの到達手段が実行時テキストに明記される。
- 実行時テキストの増分は、厚い版で 507 字・ガード版で 166 字（列挙とその打ち消しを載せていた版は 1,048 字だった）。(h) の判定軸で残るのは行動を変える文だけであり、根拠・実測値・例示・背景は本 ADR が引き受ける。
- `scripts/tests/test-doc-discovery-fallback.sh` が構造不変条件を固定する: 到達を責務に含むファイルが不変コアを持つこと、開発原則への言及が**読み替え禁止と `docs/adr/` 導線を必須で伴う**こと（導出指示での代替を選言で認めない — 塞いでいる穴が別物のため）、`ドキュメントマップ` に言及するファイルの全称条件（到達手段を持つか、節の不在を既定として扱う許可リストに属するか）とその**逆方向**、旧来の硬直依存 `ドキュメントマップから` の不在、ADR 置き場の既定フォールバック、旧世代経路の残存、**探索の判定が形で書かれていること**（形の基準・リコール優先・全件列挙・パス全体の考慮・探索先ディレクトリが `docs/` 決め打ちでないこと）、**ファイル名パターンの列挙が実行時テキストに無いこと**（条件付きではなく直接の不在。検出器の自己検査つき）、および**厚みが役割に応じて分かれていること**（ガード側が探索手順を持たないこと・2集合が素であること）。
- **本 ADR は実行時ファイルから参照しない**（(f) の参照禁止）。規範は各実行時ファイルにインラインで書き切ってある。
