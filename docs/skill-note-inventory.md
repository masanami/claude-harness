# スキル定義の定型注記 — 到達性による棚卸し（Issue #179）

`skills/` `agents/` に逐語コピーで散在する定型注記を、**到達性**（実行時にその内容が届くか）と**強制可能性**（機械が守れるか）で棚卸しした記録。判断の根拠と、機械へ移した規約の所在を残す。

規約そのものの正本は `docs/plugin-path-conventions.md`。本文書は「なぜその形にしたか」の棚卸し記録であり、規範の正本ではない。

## 1. 結論（先に）

| 論点 | 結論 |
|---|---|
| 正本1箇所＋各スキルは1行参照へ集約するか | **しない**。参照先（`references/`）は headless 委譲では既定で読めず、集約すると規約が1バイトも届かなくなる |
| 逐語コピーを正本とバイト一致で照合するか | **しない**。呼び出し箇所ごとに正当に異なる部分を潰し、PR #176 と同種の回帰を作る |
| 代わりに何をするか | **不変コアの節だけを機械で固定**し、可変部は自由に残す。加えて**規約をスクリプト側の設計へ移す**（誤った形が動かない／黙って失敗しない） |
| 「予防的に足しただけの注記」は見つかったか | **ほぼ無い**。全節が実測事故か既存テストのいずれかに紐づいた（詳細は §4） |

## 3. 分類の基準

Issue #179 が挙げた3分類（事故記録あり／予防的／スクリプト化で解決済み）は**注記ブロック単位では判定できない**。1ブロックは複数の節の合成であり、節ごとに事情が違うためである（例: 同じブロック内に「引数のパスは引用符で囲む」と「非信頼値はシングルクォート」が同居し、前者を機械的に横展開すると後者を壊す＝ PR #176 の回帰）。

そこで**節（clause）単位**で、次の3分類に割り当てた。

| 分類 | 定義 | 扱い |
|---|---|---|
| **(a) 機械が守れる規約** | 違反形を静的に検出できる、または誤った形が実行時に失敗する | スクリプト／テストへ移す。注記は「なぜその形か」を残す |
| **(b) 判断が要る規約** | 実行時のモデルの振る舞いに依存し、静的検査では守れない | 注記として残す。節の**存在**だけを機械で固定する |
| **(c) 読めなくても成果が壊れない補足** | 欠けても成果物が壊れない説明・理由 | 残す（削除しない。理由は §4 末尾） |

### (c) について — 「予防的に足しただけの注記」は見つからなかった

厳密に「欠けても成果物が壊れないか」で判定すると (c) に落ちるのは**理由の説明部分だけ**である（例:「空白を含むパスで引数が分割され `too many arguments` で exit 2 になるのを防ぐため」「引数側の引用符は allowlist のマッチに影響しない」）。

## 5-2. 独立敵対レビューで判明した「沈黙の残り」

実装に関与していない独立セッションが PR を敵対的にレビューし、**この PR の目的（沈黙する失敗を潰す）が、最も本文が大きい参照ファイルに対して達成されていない**ことを実測で示した。要点と対処:

| 指摘 | 実測された事実 | 対処 |
|---|---|---|
| **出力上限で本文が黙って切れる** | 53,017 バイトのファイルで、モデルに届いたのは先頭 2KB のみ。stderr のレシートは末尾にあるため切り詰めで消え、exit code は 0。注記が命じる停止条件は「非0 終了」だけなので、注記に文字通り従うエージェントは停止しない | 開始マーカーを本文の**前**へ（切り詰めを生き延びる位置）／終端マーカーを**後ろ**へ（不在を切り詰めの検査に使う）／`--from-line` `--max-bytes` による分割配送。注記にも「終端マーカーが無ければ切り詰めとみなして停止」を追加 |
| **レシートが本文へ混入する** | Bash ツールは stdout と stderr を1つのテキストにまとめるため、「stdout は本文のみ」という契約は配送境界で消える。テンプレートを埋めて書き出す用途では成果物にレシート行が紛れうる | マーカーによる framing に変更し、注記と仕様に「マーカー行・`read-plugin-doc:` 行は本文ではない」を明記。**テストが固定していた不変条件（fd 分離）も誤りだったため差し替えた** |
| **配送元のバージョンが検証されない** | ランチャーはインストール済みの**最大バージョン**を選ぶため、旧版 SKILL.md ＋ 新版 references の混成が exit 0 で成立しうる | BEGIN マーカーと stderr レシートの両方に解決した `root` と `version` を出す |
| **検査が部分一致で通る** | 「非0 終了でも停止は不要。推測して続行してよい」へ反転しても全検査が通った | 反転しえない節は**一文まるごと**で照合し、反転語彙の不在も見る |
| **正本テンプレートが走査対象外** | 正本を緩めれば検査は緑のまま | (ix)(x) の走査対象に `docs/plugin-path-conventions.md` を追加 |
| **注記なしスキルが素通り** | `references/` を持つ新規スキルに注記が1つも無くても全検査が通った | owner スキル側からの**全称条件**へ変更 |
| **0 バイト・EPIPE・orphan の空虚な真** | いずれも「成功」または「検査済み」に化けていた | exit 66 化／SIGPIPE の個別診断／owner 込みフルパスでの照合・自己言及の除外 |
| **部分配送のレシートが全量配送と同文** | 53,017 バイト中 15,922 バイトしか出していない回で `delivered ... (53017 bytes)` と報告していた。レシートは本文の後ろに来る最後の1行で要約として読まれやすい | 完全配送と部分配送で先頭語から変え（`delivered ... complete:` / `PARTIAL ...`）、配送済み量と全体量を必ず併記する |
| **注記が参照ファイルを1本に決め打ち**（別レビュアー codex の指摘） | モード別スキル3本で、注記が常に「最初のモード」のファイルを名指ししていた。別モードを選ぶと違う手順書が届くか拒否される Read 経路へ落ちる。**注記と本文のモード表という2つの規則が食い違っていた** | 注記の配送コマンドとフォールバック Read パスをプレースホルダにし、具体パスはモード表が持つ形へ（該当5スキル）。表のパスもプラグインルート相対へ揃え、注記直後の「Read し」を配送経路の表現に直した |

**セキュリティ境界は突破されなかった**（絶対パス・`..`・中間 `..`・symlink・dir symlink・mode 000・`.md` 名のディレクトリ・allowlist 外の12パターンをレビューが実測し、すべて非0・本文非出力）。この設計は変更していない。

### 規模の増減（正直な会計）

読み出し注記の移行で **+10.2KB**（10箇所 / 移行前 3.4KB → 移行後 13.7KB）。Issue #179 が期待した「36.6KB → 数百バイト」とは逆方向である。

これを妥当と判断した根拠:

- Issue 自身が「コンテキスト消費は主要な問題ではない」と評価しており、**1回の実行で読むのは1スキル分＝約 1.4KB**

- 増えた分は到達性（配送経路）と失敗の可視化（停止規則）に使われており、いずれも実測された沈黙する失敗への対処
