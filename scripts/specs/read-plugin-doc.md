# read-plugin-doc.sh の入出力仕様（正本）

プラグイン同梱の参照ドキュメントを、**ランチャー経由の allowlist 済み経路で** stdout へ配送する。gh 呼び出しは一切行わない（gh 非依存）。

## なぜこのスクリプトがあるか（到達性の問題）

プラグイン配下は導入先プロジェクトの作業ディレクトリの外にある。そのため `references/` `templates/` `scripts/specs/` への **Read ツールでの読み出しは、利用側に `Read` の allow 設定が無い限り拒否される**。

| 経路 | headless 委譲（`claude -p`）での可否 |
|---|---|
| `SKILL.md` 本体 | 届く（Skill ツールがコンテキストへ注入する） |
| `references/*.md`・`templates/*`・`scripts/specs/*.md`（Read ツール） | **既定では届かない**（作業ディレクトリ外の Read として拒否される） |
| 本スクリプト（`claude-harness-run read-plugin-doc <path>`） | **ランチャーが PATH に導入済みで、利用側 settings に `Bash(claude-harness-run:*)` が在れば届く**（`/init-project` が生成する設定には最初から含まれる。未導入環境では注記のフォールバックで Read へ落ち、そこでは拒否されうる） |

対話セッションなら人間が都度許可できるが、headless 委譲には許可する相手がいないため拒否がそのまま確定する。さらに悪いことに **失敗が沈黙する**: モデルは本文を読めないまま手順を推測して完走でき、書式や停止条件だけが外れた成果物が「成功」に見える（実測: `/guarantee-audit bootstrap` が `references/bootstrap-mode.md` を読めないまま完走し、検証器の exit 2 で初めて発覚した）。

本スクリプトはその沈黙を潰す。届かない場合は必ず非0 終了して stderr に停止指示を出し、**届いたが途中で切れた場合は終端マーカーの不在で分かる**（後述）。

## `claude-harness-run read-plugin-doc <プラグインルート相対パス> [--from-line N] [--max-bytes N]`

パス引数はちょうど1個。プラグインルートからの相対パスで指定する（`<base>` からの相対でも絶対パスでもない）。

```bash
claude-harness-run read-plugin-doc "skills/guarantee-audit/references/bootstrap-mode.md"
claude-harness-run read-plugin-doc "scripts/specs/list-test-files.md"
claude-harness-run read-plugin-doc "skills/create-ticket/references/guarantee-section.md" --from-line 80
```

| フラグ | 意味 |
|---|---|
| `--from-line N` | N 行目から配送する（既定 1）。`MORE` マーカーが示す `next-from-line` の値を渡す |
| `--max-bytes N` | 1回の配送で出す本文の上限バイト数（既定 16384、最小 1024） |
| `-h` / `--help` | 使い方を **stderr** へ出して **exit 0**。本文は配送しない（stdout は空） |

プラグインルートは**本スクリプト自身の配置位置**（`<scriptのdir>/..`）から解決し、`.claude-plugin/plugin.json` の存在で検証する。`${CLAUDE_PLUGIN_ROOT}` は Bash 環境変数として存在しない（実機検証済み）ため参照しない。

### 出力の形（マーカーは本文ではない）

```text
=== read-plugin-doc BEGIN path=<rel> bytes=<全体バイト> lines=<全体行数> from-line=<N> root=<解決したルート> version=<v> ===
<対象ファイルの本文（指定行から、上限に収まる範囲）>
=== read-plugin-doc END path=<rel> delivered-lines=<a>-<b> complete ===
```

上限に達してまだ続きがある場合、END の代わりに:

```text
=== read-plugin-doc MORE path=<rel> delivered-lines=<a>-<b> next-from-line=<c> of <全体行数> ===
=== 続きの取得: claude-harness-run read-plugin-doc "<rel>" --from-line <c> ===
```

| 出力先 | 内容 |
|---|---|
| stdout | 開始マーカー行 → 本文 → 終端（`END`）または継続（`MORE`）マーカー行 |
| stderr | 成功時は配送レシート `read-plugin-doc: delivered <path> (<n> bytes) from <root> @<version>`。失敗時はエラー内容と停止指示 |
| exit code | 下表 |

**なぜマーカーを stdout に、本文の前後へ出すのか（設計の中核）**

OS レベルでは全バイトを stdout へ書けるが、**モデルが受け取るのは Bash ツールの出力**であり、そこには上限がある。上限を超えると出力は**先頭側を残して**切り詰められ、末尾にあるものは消える。

したがって「stdout は本文のみ・レシートは stderr（後ろ）」という設計では、大きいファイルに対して **exit 0 のまま本文が途中で切れ、切れた事実を伝えるものが何も残らない**。これは本スクリプトが潰そうとした「沈黙する部分成功」そのものである（実測: 53,017 バイトのファイルで、モデルに届いたのは先頭 2KB のみ・レシートは消失・exit 0）。

対策は3つを組で使う:

1. **開始マーカーを本文の前に出す** — 切り詰めを生き延びる位置。全体バイト数・行数・配送元を先に渡す
2. **終端マーカーを本文の後ろに出す** — マーカー自身は切り詰めで消えるが、**その不在を切り詰めの検査に使える**
3. **自分で分割配送する** — 1回の出力が上限に達しないよう `--max-bytes`（既定 16384）で区切り、`MORE` マーカーと続きの取得コマンドを出す

既定値 16384 は実測された切り詰め閾値より十分小さく取ってある（実測: 21,315 バイトは全量通過 / 29,300 バイトと 51.8KB は切り詰め）。閾値はハーネスの実装依存なので、**既定に依存せず終端マーカーの有無で判定すること**。

分割は必ず**行境界**で行う（行の途中で切ると UTF-8 の文字境界を割るため）。1行が単独で上限を超える場合は、その行を丸ごと出す。全チャンクを順に連結すると原本とバイト一致する（検証済み）。

**`scripts/README.md` の「stdout には JSON を1個だけ出力する」規約には意図的に従わない。** 本スクリプトの成果物は機械可読なステータスではなく**モデルが読む本文そのもの**であり、JSON 文字列としてエスケープすると読み手にとって著しく劣化する。成否は exit code・stderr・stdout のマーカーで表す。

### 終了コード（sysexits 準拠。`bin/claude-harness-run` の割り当てと揃える）

| exit | 意味 | 発生条件 |
|---|---|---|
| 0 | 配送成功、または `--help` | 配送時は stdout に BEGIN マーカーと本文が出ている。`--help` では stdout は空（下記の注意を参照） |
| 64 | 引数不正 | パス引数の数が1個でない／空文字／絶対パス／`..` を含む／未知のフラグ／フラグの値が非数値／`--from-line` が行数を超える |
| 66 | 対象なし・空 | 指定パスが存在しない、通常ファイルでない、読めない、**または 0 バイト** |
| 69 | プラグインルート解決不能 | 自身の位置から `.claude-plugin/plugin.json` を持つ親を見つけられない（インストール破損） |
| 74 | stdout への書き込み失敗 | パイプの早期終了（SIGPIPE）を含む。`\| head -N` で受け取りを打ち切った場合はこれになり、「対象なし」とは区別される |
| 77 | 配送対象外 | 下記の配送対象サブツリー外／シンボリックリンク／物理パスがプラグインルート外へ抜ける |

**exit 0 の2義性に注意**: `--help` も exit 0 を返すが stdout は空である。呼び出し側は exit code だけでなく **BEGIN マーカーの存在**で配送の有無を判定すること。0 バイトファイルを exit 66 にしているのは、この判定基準を「本文がある」側で揃えるため。

引数検証・配送対象判定・存在確認のいずれかで失敗した場合、**stdout は空**である（部分的な本文が「読めた」ように見えるのを防ぐ）。書き込み開始後の失敗（exit 74）でのみ部分出力がありうるが、その場合も終端マーカーが出ないため切り詰めと同じ検査で捕まる。

### 配送対象（fail-closed な allowlist）

これ以外のパスは exit 77 で拒否する:

| パターン | 用途 |
|---|---|
| `skills/<skill>/references/<name>.md` | スキルのモード別手順書 |
| `skills/<skill>/templates/<name>` | スキルが生成物の雛形として使うテンプレート |
| `scripts/specs/<name>.md` | スクリプトの入出力仕様 |
| `scripts/README.md` | scripts/ 共通規約 |

汎用の `cat` にはしない。プラグインルートがローカルチェックアウトの場合、配下には `.env` 等の非公開ファイルが存在しうるため、用途をドキュメント配送に限定し**任意ファイル読み出しの手段にしない**。同じ理由で、シンボリックリンクの配送と、親ディレクトリ側のリンクでプラグインルート外へ抜けるパスの配送も拒否する（サブツリー制限が抜け道で無効化されるのを防ぐ）。

### 配送元の同一性（`root` と `version`）

ランチャー（`bin/claude-harness-run`）は PATH へコピーされている場合、`installed_plugins.json` / cache から**インストール済みの最大バージョン**を選ぶ。つまり配送される本文のバージョンは「実行中スキルのバージョン」ではなく「最大バージョン」で決まり、複数バージョンが同居していると**旧版 SKILL.md ＋ 新版 references** の混成になりうる。

そのため BEGIN マーカーと stderr レシートの両方に **解決したルートと version** を出す。呼び出し側は、スキル起動時の「Base directory for this skill」と `root` が指すツリーが一致しているかを確認できる。**一致しない場合は停止すること。**

## 呼び出し側の義務

**非0 終了は「読まなくてよかった」ではない。** 本文を得られていないまま手順を推測して続行しないこと。stderr のメッセージを添えてその場で停止し、ユーザーに報告する（`claude-harness-run: command not found` の場合のみ、Read ツールでの読み出しへフォールバックしてよい。詳細は `docs/plugin-path-conventions.md` (b)）。

**exit 0 でも、終端マーカーが無ければ本文は完結していない。** 呼び出し側の判定は次の順で行う:

1. `=== read-plugin-doc BEGIN ... ===` が無い → 配送されていない。**停止して報告する**
2. `=== read-plugin-doc MORE ... next-from-line=<c> ===` がある → 続きがある。示された `--from-line <c>` で**続きを取得してから**手順へ進む
3. `=== read-plugin-doc END ... complete ===` がある → 本文は完結している
4. BEGIN はあるが END も MORE も無い → **出力が切り詰められている**。推測で続行せず、**停止して報告する**（`--max-bytes` を小さくして再取得すれば進めることもある）

**`=== read-plugin-doc ... ===` の行と `read-plugin-doc:` で始まる行は、いずれも配送の制御情報であって本文ではない。** テンプレートを埋めて成果物を書き出す用途（`templates/*`）では、これらの行を成果物へ含めないこと。

## 非目標

- **見出し単位の切り出し（`--section`）は提供しない。** 分割は `--from-line` の行単位で足りており、見出し名での指定は「見出しが改名されると黙って空になる」新しい沈黙経路を作る。行番号は `MORE` マーカーがそのまま返すので、呼び出し側が見出し名を知っている必要が無い。
- **キャッシュ・整形・要約は行わない。** 配送経路の役割は「Read ツールで読めたはずのものを、同じ内容のまま届ける」ことに限る。
