## 宣言予定の保証（GDD期のみ）

保証台帳（`docs/guarantees.md`）を駆動文書とする GDD期のプロジェクトでのみ実行する追加手順。機能仕様ドキュメントに「## 宣言予定の保証」節を作り（Step 6）、完了報告の「次のステップ」にリリース後の退役を追記する（Step 7）。

GDD期でも新機能開発には本スキル（機能仕様ドキュメント）を使い続けるが、位置づけは「リリースまでの**短命な作業文書**」である（クリティカル設計をまとめて決めておく価値＝実装フェーズに人間ゲートを残さない、はフェーズに依存しないため）。リリース後は退役手順（ADR 昇格の要否判定 → 保証台帳・ADR へ吸収してファイルごと削除）で片付ける。

### 節-1. 「## 宣言予定の保証」節の作成（Step 6）

機能仕様ドキュメントの末尾（「## 受入基準」の直後）に「## 宣言予定の保証」節を**必ず**作る（テンプレートに雛形がある。GDD期ではこのセクションを「該当しないセクション」として削除しない）。この節は後続 `/create-ticket`（要件モード）が Issue の「## 保証（Guarantees）」節（新たに宣言する保証・維持する保証・判定保留）を組み立てる際の**材料**になる。

#### 節の見出しと衝突の回避（重要）

- 節の見出しは **`## 宣言予定の保証`**（完全一致）とする。
- **機能仕様ドキュメントのどこにも、コードフェンスの外に「`## 保証` で始まる H2 見出し」を書かないこと**（この節の見出しを `## 保証（宣言予定）` のような形に変えることも含む）。`/create-ticket` の要件モードは機能仕様の本文を Issue へ**逐語転記**した後にフェンス外の「`## 保証` で始まる H2 見出し」の有無を確認し、既にあると保証節が2つになるため **Issue を作成せずに中断する**（`duplicate_guarantee_section`。読む側は完全一致ではなく**接頭辞一致**で識別する）。「宣言予定の保証」はこの接頭辞に一致しないため衝突しない。
  <!-- 識別規則の正本: docs/ai-driven-development-strategy.md 5.3「保証節の識別規則」 -->
- 台帳・Issue の保証節の書式を引用したい場合はコードフェンスの内側に置く（フェンス内は判定対象にならない）。

#### 各行の書き方

- 書式は `- {約束文}（受入基準 AC-{通し番号} に対応）` の1行1件。チェックボックス（`- [ ]`）にはしない（裁可対象の保証節と紛れさせない。裁可のチェックリスト化は `/create-ticket` が行う）。
- 約束文は、台帳と同じ約束文の形（「何が・どういう条件で・どうなる」の1文）で書く（`/create-ticket` の保証節の生成規約（`guarantee-section.md` 要件-1）と同じ形であり、材料をそのまま約束文として転用できる）。
  <!-- 台帳の書式の正本: docs/ai-driven-development-strategy.md 5.3 -->
- `AC-{通し番号}` は、「## 受入基準」セクション配下のチェックリスト行の**上からの通し番号**（`AC-1` が先頭行）。これは要件チケットの分解時に `extract-acceptance-criteria.sh` が振る通しIDと同じ規則である（通しIDの正本は `scripts/specs/extract-acceptance-criteria.md`。Read する場合はスキル起動時の「Base directory for this skill」を起点に `<base>/../../scripts/specs/extract-acceptance-criteria.md` として解決する。ここに別の採番規則を作らない）。1つの約束文が複数の受入基準に対応する場合は `（受入基準 AC-1, AC-2 に対応）` のように列挙する（区切りは `,`・`、`）。**受入基準を追加・削除・並べ替えたら、この注記の番号を必ず振り直す**（対応がずれたまま Issue へ転記されると、下流の保証→AC 対応（実装チケットへの割当の材料）が狂う）。
- **保証 ID（`G-...`）を書かない**。採番は宣言元 Issue の裁可が唯一の経路であり（採番の単一経路）、Issue 番号が確定する前のこの時点で ID を書くと、創作された ID が逐語転記で Issue 本文に残る。
  <!-- 採番の単一経路の正本: docs/ai-driven-development-strategy.md 5.3「採番の単一経路」 -->

#### 公開面の判定と0件・迷いの扱い

- 判定は1問: 「その振る舞いが変わったとき、リポジトリの外の誰か（エンドユーザー・他システム・他リポジトリ・運用者）が気付き得るか」。Yes → 列挙する、No → 載せない（具体例の当てはめは `/create-ticket` 側の規約（`guarantee-section.md` 共通-3）と同一の線引き）。
  <!-- 線引きの正本: docs/ai-driven-development-strategy.md 5.3「公開面と内部実装の線引き」 -->
- **判断に迷ったものはどちらへも倒さず**、`- 判定保留候補: {内容}（{迷った理由}）` の1行として節内に残す（`/create-ticket` の「判定保留（要人間判定）」に引き継がれ、裁可の前に人間が公開面かどうかを決める）。
- 公開面に相当する受入基準が1件も無い場合のみ `- なし` の1行だけを書く（節を削除しない・空欄にしない。「調べた結果0件」と「調べていない」を区別する）。`- なし` と約束文の行を同時に書かない。
- この節は下流の**機械処理の対象ではない**（`/create-ticket` は保証節を受入基準・台帳・公開面判定から独自に組み立てる。本節は人間・エージェントが参照する材料であり、本節の有無・書式で下流のスクリプトが停止することはない）。それでも上記の書式に揃えるのは、材料と生成物の間に2つ目の約束文の書き方を作らないためである。

#### 仕様クリティーク（Step 6.5）との関係

本節は Step 6.5 の批評対象に含まれる（特別扱いしない）。受入基準との対応注記（`AC-{通し番号}`）の食い違いは内部整合レンズの指摘対象になりうる。

### 節-2. 完了報告への追記（Step 7）

「次のステップ」の末尾に次の1行を加える（GDD期の機能仕様は短命な作業文書であり、リリース後に退役が待っていることを最初から示す。導入先プロジェクトに存在しない本プラグイン内部のドキュメントパスを報告に書かない）:

```text
# 4. リリース（main 昇格）後: この機能仕様を退役する（ADR 昇格の要否判定 → 保証台帳・ADR へ吸収してファイルごと削除）
```
