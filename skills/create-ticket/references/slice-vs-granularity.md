# スライス（出荷の単位）とチケット粒度（スライス内の分割）の関係

> 人間向けの説明。`/create-ticket` の実行時には読まない（要件モードの手順は `requirement-mode.md`、実装分解モードの手順は `decompose-mode.md`）。

`/define-feature` → `/create-ticket` → `/para-impl` の流れには、大きさを決める軸が2つある。

| 軸 | 単位 | 決める場所 | 基準 |
|---|---|---|---|
| **スライス** | 出荷の単位（それだけでマージして価値が出る縦切り） | `/define-feature` 手順 2-1 → 機能仕様の「## スライス（出荷の単位）」 | S1 はそれだけで価値が出る最小の縦切り。S2 以降は前スライスの PR がマージされてから |
| **粒度** | スライス**内**のタスク分割（1 エージェントで完結・1 PR・明確な完了条件・依存最小） | `/create-ticket` 実装分解モード → `agents/ticket-decomposer.md` の粒度基準（`<!-- granularity-criteria:start -->` 〜 `<!-- granularity-criteria:end -->`） | 変更しない。親 Issue = 1 スライスの中を分ける基準としてそのまま機能する |

## 対応関係

- **1 スライス = 1 要件チケット（親 Issue）**。要件モードは機能仕様の `実装対象:` 行のスライス（既定 S1）だけを起票する。後続スライスは起票せず、機能仕様のスライス表に残す。
- **親 Issue の中の分割は粒度基準に従う**。実装分解モードは親 Issue 本文だけを読み、受入基準（実装対象スライスの範囲に収められている）を網羅するタスク群を作る。`vertical-slice` レンズの「最小の縦切り」はこの**スライス内**の分割方針であり、出荷単位のスライスとは別物。
- **受入基準は実装対象スライスの範囲に収める**。`spec-critic` の `internal-consistency` レンズが、後続スライスや「やらないこと」を検証する受入基準を指摘する。

## 後続スライスの起票

- トリガー: **前スライスの PR がマージされた後**。
- 実行主体: **人間の手動、または呼び出し側フロー**（`/pr-merge` の後処理には組み込まない。マージの時点で「S2 は要らない」「方向を変える」を人間が選べる再同期点を残すため）。
- 手順: 機能仕様の `実装対象:` を次のスライス ID へ進め、「## 受入基準」をそのスライスの範囲に書き直し（`/define-feature` の再実行または直接編集。編集後は 6.5 の仕様クリティークを通す）、`/create-ticket <機能仕様パス>` を再実行する。Issue タイトル末尾の `（S2）` で前スライスの Issue と区別する。
- 出荷済みスライスの受入基準は当該スライスの Issue 本文（機能仕様の再掲）とテストが保持する。機能仕様側の「## 受入基準」には実装対象スライスの基準だけを置く。

## 旧テンプレートの機能仕様

「## スライス（出荷の単位）」が無い機能仕様は、要件モードが従来どおり仕様全体を 1 チケットとして起票する（後方互換）。スライスに切りたい場合は `/define-feature` を再実行して節を足す。
