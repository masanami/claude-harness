## 要件モード（機能仕様 → 親チケット）

### Step 1: 機能仕様ドキュメントの読み込み

引数のパスから機能仕様ドキュメントを読み込む。ドキュメントには以下が含まれる前提:

- 概要・背景・ユーザーストーリー
- 機能要件 / 非機能要件
- **クリティカル設計決定**（該当する場合）
- 機能全体の設計（複雑な機能のみ）
- 受入基準

足りないセクションがあれば `/define-feature` への差し戻しを案内する。

### Step 2: Issue 本文の構成

Issue 本文は次の形にする（機能仕様の内容をそのまま使う）:

```text
> 機能仕様: {入力された機能仕様ドキュメントパス}

{機能仕様ドキュメントの本文をそのまま貼り付け}
```

機能仕様へのリンクを冒頭に置き、本文を再掲する（GitHub 上での閲覧性のため）。

> **GDD期のみ（SKILL.md のフェーズ判定が `gdd` の場合）**: 上記の本文の末尾に「## 保証（Guarantees）」節を**必須**で含める。節の書式・新たに宣言する保証／維持する保証の作り方・判定保留の扱い・台帳の読み取り規則は参照ファイル `references/guarantee-section.md`（共通-1〜共通-3・要件-1）が正本であり、そちらを Read して従うこと。`sdd`（フェーズ宣言なしを含む）では本項を実行せず、本文は上記のみとする。

### Step 3: GitHub Issue 作成

```bash
gh issue create \
  --title "{機能仕様のタイトル(機能名)}" \
  --body "$(cat <<'EOF'
{Step 2 で構成した本文}
EOF
)" \
  --label "requirement"
```

ラベルはプロジェクトの慣習に従う（`requirement` が無ければ作成 or 別名を使用）。

> **GDD期のみ（SKILL.md のフェーズ判定が `gdd` の場合）**: 上記の作成コマンドに `--label "guarantee:proposed"`（裁可待ちの表示）を加え、作成 → 保証 ID のプレースホルダ置換 → 検証の3ステップを通す。ラベル定義の用意・裁可ラベルの運用（人間が `guarantee:approved` へ付け替える／エージェントは付けない）・失敗時の要人間対応の報告項目は参照ファイル `references/guarantee-section.md`（要件-2・要件-3）が正本であり、そちらを Read して従うこと。`sdd`（フェーズ宣言なしを含む）では本項を実行せず、上記のコマンドのままとする。

### Step 4: 完了報告（要件モード）

```text
## 要件チケット作成 完了

- 親要件チケット: #{番号}
- 機能仕様: {入力された機能仕様ドキュメントパス}

次のステップ:
# 実装チケットに分解
/create-ticket {番号}
```

> **GDD期のみ（SKILL.md のフェーズ判定が `gdd` の場合）**: 上記の報告に「## 保証（GDD期）」節（裁可状態・新たに宣言する保証・維持する保証・判定保留・索引整合チェック・次に人間が行う操作）を足す。書式と `裁可状態` の決め方は参照ファイル `references/guarantee-section.md`（要件-4）が正本であり、そちらを Read して従うこと。`sdd`（フェーズ宣言なしを含む）では本項を実行せず、報告は上記のみとする。
