## 要件モード（機能仕様 → 親チケット）

### Step 1: 機能仕様ドキュメントの読み込み

引数のパスから機能仕様ドキュメントを読み込む。ドキュメントには以下が含まれる前提:

- 概要・背景・ユーザーストーリー
- 機能要件 / 非機能要件
- **クリティカル設計決定**（該当する場合）
- 機能全体の設計（複雑な機能のみ）
- **スライス（出荷の単位）**（スライス表と `実装対象: {ID}` の行）
- **やらないこと**
- 受入基準

足りないセクションがあれば `/define-feature` への差し戻しを案内する。

#### 1-1. 実装対象スライスの特定（1スライス = 1チケット）

- 「## スライス（出荷の単位）」が在れば、`実装対象:` 行のスライス ID（既定 `S1`）を**実装対象スライス**とし、スライス表から当該行の「内容」「触るファイル数（概算）」を読む。`実装対象:` 行が無ければ S1 を実装対象とする
- **起票するのは実装対象スライスの要件チケット1件のみ**。後続スライス（S2 以降）のチケットは起票しない（機能仕様のスライス表に残す）
- **後続スライスの起票トリガーは「前スライスの PR がマージされた後」**。起票の実行主体は**人間の手動、または呼び出し側フロー**であり、本スキルも `/pr-merge` も自動では起票しない。起票する側は、機能仕様の `実装対象:` を次のスライスへ進め、「## 受入基準」をそのスライスの範囲に書き直してから、本スキルを同じ機能仕様パスで再実行する
- 「## スライス（出荷の単位）」が無い機能仕様は、**従来どおり仕様全体を1チケット**として起票する（スライス ID は付けない）

### Step 2: Issue 本文の構成

Issue 本文は次の形にする（機能仕様の内容をそのまま使う）:

```text
> 機能仕様: {入力された機能仕様ドキュメントパス}
> スライス: {実装対象スライス ID}（{スライス表の当該行の「内容」}）。本チケットの範囲はこのスライスのみ。スライス表の他の行（後続スライス）と「やらないこと」は本チケットの範囲外であり、後続スライスは本チケットの PR がマージされた後に起票する。

{機能仕様ドキュメントの本文をそのまま貼り付け}
```

機能仕様へのリンクを冒頭に置き、本文を再掲する（GitHub 上での閲覧性のため）。`> スライス:` 行は Step 1-1 で実装対象スライスを特定できた場合のみ置く（スライス表が無い機能仕様では省く）。本文は後続スライスの行を含めてそのまま貼り付け、削らない（実装分解モードは親 Issue 本文だけを読むため、範囲の宣言は冒頭の `> スライス:` 行が担う）。

### Step 3: GitHub Issue 作成

```bash
gh issue create \
  --title "{機能仕様のタイトル(機能名)}（{実装対象スライス ID}）" \
  --body "$(cat <<'EOF'
{Step 2 で構成した本文}
EOF
)" \
  --label "requirement"
```

ラベルはプロジェクトの慣習に従う（`requirement` が無ければ作成 or 別名を使用）。タイトル末尾の `（{実装対象スライス ID}）` は同じ機能仕様から後続スライスを起票したときに区別するためのもので、スライス表が無い機能仕様では付けない。

### Step 4: 完了報告（要件モード）

```text
## 要件チケット作成 完了

- 親要件チケット: #{番号}
- 機能仕様: {入力された機能仕様ドキュメントパス}
- 実装対象スライス: {実装対象スライス ID}（{内容}／触るファイル数（概算） {N}）
- 後続スライス: {S2 … の一覧。無ければ「なし」}（起票は本チケットの PR がマージされた後。人間または呼び出し側フローが機能仕様の `実装対象:` を進めて本スキルを再実行する）

次のステップ:
# 実装チケットに分解
/create-ticket {番号}
```
