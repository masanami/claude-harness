## 昇格判定モード（退役する機能仕様 → ADR 昇格の要否）

退役（削除）予定の機能仕様を読み、**ADR に昇格すべき恒常的決定が残っていないか**を全件判定する。

> **本ファイルの前提**: 起動引数の解釈は SKILL.md 側で完了している前提で読むこと。**何を ADR にするかの線引き（3条件）・置き場と採番・構成とステータス・改訂の扱い・ドキュメントマップへの反映は SKILL.md の「共通規約」が正本**であり、本ファイルには複製しない。

> **このモードの位置づけ（重要）**: 機能仕様の削除は不可逆であり、**ここが設計決定を拾う最後の機会**である。したがって判定の目的は「削除して良いか」の確認ではなく、「**昇格させるべき決定が残っていないか**」の確認である。判定結果が「昇格不要」でも構わないが、**判定そのものを省略しない**。「判定していない」と「判定した結果、不要だった」を報告上で必ず区別すること。

> **本モードは仕様ファイルを削除しない**。削除は退役作業（人間の PR）の責務であり、本スキルは判定と昇格までを行う（判定と削除の分離）。

**fan-out（サブエージェントへの委譲）は行わず、リード自身が対象を読む。** 同じ決定が複数の仕様に重複して現れるため、統合判断には単一コンテキストが要る。対象が多い場合はチャンクに区切って順に読み進め、Step P1 で固定した対象一覧との突き合わせで網羅性を担保する。

### Step P1: 対象の確定（件数を固定する）

1. 引数のパス・ディレクトリを展開し、**判定対象の一覧を確定する**（ディレクトリは直下の `*.md` のみ。再帰しない）。
2. 対象が0件の場合は**停止して報告する**（「対象0件」を「昇格不要」と読み替えない。パス指定の誤りである可能性が高い）。
3. 確定した一覧の**件数を控える**。以降の全ステップは、この一覧の全件に対して結果を持つ。
4. `CLAUDE.md` を読み、ADR の置き場（別パス指定の有無）と、既存の保証台帳（`docs/guarantees.md` 等）・恒常設計ドキュメントの所在を把握する。

### Step P2: 決定候補の抽出（対象1件ごとに状態を持つ）

対象の各仕様を Read し、次を抽出する:

- 「クリティカル設計決定」に相当する記述（認可モデル・スキーマ方針・外部 API 契約・アーキ判断 等）
- 明示の見出しが無くても、**今後の実装が従うべき規範として書かれている記述**
- 採用理由・却下した代替案の記述（ADR の「検討した代替案」の材料になる）

**各対象について次の状態を必ず持つ**（集約値と別に保持する）:

| 状態 | 意味 |
|---|---|
| `judged` | 全文を読み、抽出と判定を完了した |
| `unreadable` | ファイルが読めない（存在しない・権限・破損） |
| `indeterminate` | 読めたが記述が断片的で、昇格の要否を判断できない |

- **`unreadable` / `indeterminate` を「昇格不要」に切り上げない**。要人間判定として Step P5 に列挙する。
- 対象全件が `judged` にならない限り、**「昇格すべき決定は無い」という結論を出さない**（結論は「判定できた範囲では無い」という下限として提示する）。

### Step P3: 3条件による判定と重複の統合

抽出した各候補に、SKILL.md「共通規約」の3条件（恒常性・非自明性・選択性）と1問テストを当てる。

- **既存 ADR との重複**を確認する。すでに同じ問いの ADR がある候補は「昇格不要（ADR NNNN に既出）」とする。元 ADR の記述が古い場合は共通規約の改訂ルールで処理する。
- **委ね先が別にある候補**は昇格不要とし、委ね先を明記する:

  | 候補の性質 | 委ね先 |
  |---|---|
  | すでに守っている公開面の振る舞い | 保証台帳（`docs/guarantees.md`）。台帳に無ければ **Gap として報告**する（黙って捨てない） |
  | その機能限りの要件・受入基準 | 宣言元 Issue（削除後も Issue から追える） |
  | 実装の内部設計・アルゴリズム選択 | コードとテスト |
  | 恒常的だが既存の恒常設計ドキュメントに記載済み | そのドキュメント |

- **複数の仕様に同じ決定が現れる場合は1件の ADR に統合する**（仕様1件につき ADR 1件にしない）。統合した場合は、どの仕様に由来するかを ADR の「関連」に列挙する。

### Step P4: 昇格対象の ADR 化

昇格対象が**1件以上ある場合のみ**、各決定について `references/record-mode.md` の **Step R3（既存 ADR との突き合わせ）〜 Step R4（執筆）** に従って ADR を作成・改訂する（採番・テンプレート・執筆規律はそちらに従う。ここには複製しない）。

- 退役元の仕様パスと関連 Issue/PR 番号を、ADR の「関連」メタ情報に必ず残す（削除後もトレーサビリティが切れないようにするため）。
- 決定内容が仕様の記述だけでは不足する場合（背景・代替案が書かれていない等）は、関連コード・Issue を確認して補う。**それでも埋まらない項目は推測で埋めず、「未検証の前提」として明示する**。
- 昇格対象が0件の場合は ADR を作らない。その場合も Step P5 の判定表は必ず出力する。

### Step P5: 判定表の出力と完了報告

**判定表は退役 PR の本文に貼る前提**で出力する（レビュアーが「昇格させるべきものが残っていないか」を確認できるようにするため）。**Step P1 で固定した対象一覧の全件を、1件も省略せずに載せる**。

```text
## ADR 昇格の要否判定

対象: {N} 件（判定完了 {N_judged} 件 / 要人間判定 {N_pending} 件）

| 機能仕様 | 判定 | 昇格先 / 委ね先 | 理由 |
|---|---|---|---|
| docs/features/{slug}.md | 昇格あり | docs/adr/{NNNN}-{slug}.md | {3条件を満たした決定の要約} |
| docs/features/{slug2}.md | 昇格不要 | 保証台帳 / 宣言元 Issue #{n} / コード | {3条件のどれを満たさなかったか} |
| docs/features/{slug3}.md | 要人間判定 | — | {unreadable / indeterminate の内容} |

### 台帳の Gap 候補（公開面だが保証台帳に見当たらない）
- {内容}（由来: docs/features/{slug}.md）

### 未検証の前提（ADR に明示したもの）
- {内容}
```

完了報告:

```text
## ADR 昇格判定 完了

- 判定対象: {N} 件（判定完了 {N_judged} / 要人間判定 {N_pending}）
- 作成した ADR: {パス一覧。0件なら「なし（判定の結果、昇格対象なし）」}
- 改訂した ADR: {パス一覧。無ければ「なし」}
- CLAUDE.md ドキュメントマップ: {追記した | 既に行がある | 表が無いため未追記 | ADR 未作成のため対象外}

注意:
- 本スキルは機能仕様の削除を行いません。削除は退役 PR で実施してください。
- 上記の判定表を退役 PR の本文に含めてください（レビュー観点は「削除して良いか」ではなく「昇格させるべき決定が残っていないか」です）。
- 要人間判定が残っている場合、その仕様は**削除せず**判定を先に解消してください。

次のステップ:
- 作成・改訂した ADR を確認のうえ /commit でコミットしてください（本スキルはコミット・PR 作成を行いません）
```
