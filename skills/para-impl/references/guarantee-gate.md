## Phase 1: 裁可ゲート（前提未充足での停止）

**統合ブランチ存在チェックと同じ「前提未充足での停止」パターンを使う**——満たされていなければ処理を止め、人間が行う操作を示して終了する。**新しい待ち合わせ機構（裁可待ちのポーリング・ラベル変更の監視）は作らない**。

### 1-a. 裁可対象の解決（対象 Issue ごと）

Phase 1 で取得済みの各 Issue 本文の冒頭ヘッダ行（テンプレート `implementation-ticket.md` の書式 `Parent: #{親チケット番号}`・`保証: 親#{親チケット番号} の保証節参照`）から裁可対象を決める。ヘッダ行はコードフェンスの外・本文冒頭部にあるものだけを読む（本文中の引用・書式例を拾わない）。**本文冒頭部とは、本文先頭から最初の見出し行（`#` 始まり）までの範囲**を指す（テンプレート `implementation-ticket.md` のヘッダ行群はすべてこの範囲にある。`対応する受入基準:` 行を含め、以降で「ヘッダ行」と呼ぶものはすべてこの規律で読む）:

| 本文の状態 | 裁可対象 |
|---|---|
| `Parent: #<N>` 行と `保証: 親#<M> の保証節参照` 行があり N = M | 親 Issue `#<N>` |
| `Parent: #<N>` 行のみ（`保証:` 行なし） | 親 Issue `#<N>` |
| `保証: 親#<M> の保証節参照` 行のみ | 親 Issue `#<M>` |
| どちらの行も無い（要件チケット・単独タスク） | 対象 Issue 自身 |
| `Parent: #<N>` と `保証: 親#<M>` の番号が食い違う（N ≠ M） | **解決不能**（判定表 #1。どちらかを勝手に採用しない） |

### 1-b. ラベルの取得と判定

裁可対象ごとに `gh issue view {裁可対象番号} --json labels` でラベル一覧を取得し、`name` の**完全一致**で判定する（**接頭辞・部分一致で通さない**。別ラベルや似た名前のラベルを裁可と誤認しない）。

**判定表（各行は排他。上から順に評価し、最初に該当した行で確定する）**:

| # | 状態 | 動作 | `reason` |
|---|---|---|---|
| 1 | 裁可対象を解決できない（`Parent:` 行と `保証:` 行の親番号の食い違い） | **停止**（同一性が成立しない Issue を実装しない） | `parent_mismatch` |
| 2 | ラベル一覧を取得できない（Issue が存在しない・取得エラー・出力がパース不能） | **停止**（**検査不能を「ラベルなし」に読み替えない**。報告では「確認できず」と裁可待ちを区別する） | `labels_unavailable` |
| 3 | `guarantee:approved` と `guarantee:proposed` の両方が付いている | **停止**（裁可の付け替え——`guarantee:proposed` を外す——が完了していない中間状態。裁可済みとみなさない） | `label_state_ambiguous` |
| 4 | `guarantee:approved` が完全一致で付いている（`guarantee:proposed` は無い） | **ゲート通過**（当該 Issue は実装してよい） | — |
| 5 | `guarantee:approved` が無い（`guarantee:proposed` のみ・どちらも無いを含む） | **停止**（人間の裁可待ち） | `approval_missing` |

### 1-c. 複数 Issue の扱い（部分成功≠完全成功）

- **全対象 Issue の判定を先に終えてから**次へ進む（1件目の停止で残りの判定を打ち切らず、停止報告に全 Issue の判定結果を列挙する）。
- **1件でも「停止」に該当する Issue があれば、Phase 2 以降へ進まず全体を停止する**（裁可済みの Issue だけを先に実装しない。裁可漏れはチケット分解・裁可運用の異常の兆候であり、部分実行すると停止分の扱いが宙に浮く）。
- 判定できなかった Issue（`labels_unavailable`）を「問題なし」に数えない。

### 1-d. 停止時の報告（すべての `reason` に共通の形式。項目を省略・推測で埋めない）

```text
## 実装を開始していません（GDD期・前提未充足）

| 対象 Issue | 裁可対象 | 判定 | reason | 現在のラベル |
|---|---|---|---|---|
| #{番号} | #{裁可対象番号} | 通過 / 停止 / 対象外（base が SDD期） | {reason コード} / — | {ラベル一覧。取得できなければ「確認できず」} |

- 人間が行う操作と再開方法: {語彙表の当該 reason の「人間の対処と再開」列の内容。停止が複数 reason にわたる場合は reason ごとに書く}
```

**表の形式は全 `reason` に共通だが、「人間が行う操作と再開方法」は reason ごとに異なる——語彙表（下表）の「人間の対処と再開」列が正本であり、これ以外に共通の固定手順を置かない**（reason に無関係な操作——例: 分解済み親の停止にラベルの付け替えや同じ親番号での再実行を促す——を指示しない）。**Phase 4-5 の停止も本形式・本表に従う**。

**`reason` コードの語彙（この表が正本。増減するときは判定表・停止時の報告・Phase 4-5 の停止条件を必ず同時に更新する）**:

| `reason` | 適用フェーズ | 停止する条件 | 人間の対処と再開 |
|---|---|---|---|
| `parent_mismatch` | Phase 1 | `Parent:` 行と `保証:` 行の親 Issue 番号が食い違い、裁可対象を解決できない | 対象 Issue のヘッダ行（`Parent:`／`保証:`）の親番号を正しく修正し、`/para-impl {対象 Issue 番号}` を再実行する |
| `labels_unavailable` | Phase 1 | 裁可対象のラベル一覧を取得できない（検査不能。「ラベルなし」に読み替えない） | 裁可対象 Issue の存在と gh の認証・接続を確認し、`/para-impl {対象 Issue 番号}` を再実行する |
| `label_state_ambiguous` | Phase 1 | `guarantee:approved` と `guarantee:proposed` が同時に付いている | 裁可対象 Issue の裁可状態を確認し、承認済みなら `guarantee:proposed` を外して表示を一意にする。その後 `/para-impl {対象 Issue 番号}` を再実行する |
| `approval_missing` | Phase 1 | `guarantee:approved` が付いていない（人間の裁可待ち） | 裁可対象 Issue の保証節をレビューし、承認するなら `guarantee:proposed` を外して `guarantee:approved` に付け替える（GitHub の UI から、または gh issue edit のラベル操作で行う。付け替えは人間の操作であり、このコマンドをエージェントが代行しない）。その後 `/para-impl {対象 Issue 番号}` を再実行する |
| `guarantee_section_unreadable` | Phase 4-5 | 裁可対象の本文に保証節が無い・親Issue本文の文法で解釈できない（裁可済みなのに節を読めないのは運用前提の破れ） | 裁可対象 Issue の保証節を要件モードの書式に整備（人間の編集、または `/create-ticket` のやり直し）し、必要なら再裁可のうえ再実行する |
| `guarantee_scope_mismatch` | Phase 4-5 | 新規宣言の ID が `G-<裁可対象番号>-<枝番>` の完全文法に一致しない | 裁可対象 Issue の保証節の ID を正しいスコープ・文法に修正して再裁可し、再実行する |
| `guarantee_assignment_unresolvable` | Phase 4-5 | 新規宣言の担当割当を決定的規則で一意に導出できない ID がある（対応 AC 注記の欠落・`対応する受入基準:` 行を持たないチケットの存在・候補チケット0件・注記を解釈できない） | 実装チケットの `対応する受入基準:` 行の整備、または分解の見直し（`/create-ticket` の再実行）を行い、再実行する |
| `decomposition_unverifiable` | Phase 4-5 | 実装チケット起動で、採用後の兄弟集合に対象 Issue 自身が含まれない（0件・照会失敗を含む。分解の全体像を検証できない）。または要件チケット起動の子照会が `fallback_truncated`（打ち切りの可能性）／`children_lookup_failed`（照会失敗を含む0件）で、未分解であることを証明できない | gh の認証・接続と分解の状態（Sub-issue 連携・`Parent:` ヘッダ）を確認し（打ち切りの場合は分解の規模を確認し）、再実行する |
| `parent_already_decomposed` | Phase 4-5 | 対象が要件チケット自体だが、検証済みの子チケットが1件以上ある（分解済みの親への直接起動。実装の単位は子チケットであり、親への全量注入は第2実装の重複を生む） | ラベル操作は不要。停止報告に列挙された検証済みの子チケット番号を使い、`/para-impl {子番号...}` を再実行する |
| `ledger_unreadable` | Phase 4-5 | base リビジョンの台帳（`docs/guarantees.md`）から登録済みの保証一覧を取得できず、新規宣言の登録済み判定（担当済みの除外）を行えない（`git show` が非0・索引チェックが exit 2・stdout がパース不能） | base の `docs/guarantees.md` を整備（`/guarantee-audit bootstrap` → 人間の裁可 PR）し、`jq`・ランチャーの導入状況を確認してから再実行する |

## Phase 4-5: 保証節の注入（保証ブリーフ）

リードは「クリティカル設計決定」セクションと同様に、**裁可対象（親）Issue の保証節（新規宣言＋維持）を `feature-implementer` への委譲プロンプトに含める**。

### 読み取り文法（3つ目の独自解釈を作らない）

裁可対象 Issue 本文の保証節の読み取り文法の**正本は `<base>/../create-ticket/references/guarantee-section.md` の「共通-2. 読み取り規則」**——(a) 文法に依存しない共通部分と (c) 親Issue本文の文法——であり、Read して従うこと（**(b) 台帳の読み取り＝索引チェックを親Issue本文へ向けない**。カテゴリ見出しは ID 書式を満たさないため全件が `malformed_guarantee_id` になり、保証 ID を1件も取り出せない）。下流の `/promote-verify`（Step 5.5-3）も同じ文法で読む。**本ファイルには文法を複製しない**（生成側・検証側・注入側が同じ1つの規則を読む）。

### 新規宣言の担当割当（親が複数の実装チケットに分解されている場合）

**割当の要否は、今回の起動形態（同時か1件ずつか・star 型か単独か）ではなく、裁可対象（親）の構造——親が複数の実装チケットに分解されているか——で決める。** 起動形態で決めると、分解済みの親に対して 1 チケットだけを逐次起動した回で親の新規宣言の全量が注入され、後で別の子を実行したときに同じテスト作成・同じ台帳追記・ID の重複が再発する。

対象 Issue の `Parent:`／`保証:` 行の不在（1-a の解決で裁可対象＝自分）は「対象が要件チケット（親）である」ことしか証明せず、**「未分解である」ことは証明しない**（裁可済みの親は既に実装チケットへ分解された後でありうる。分解済みの親へ全量を注入すると、子チケット群のテスト・台帳更新と重複する第2実装が生まれる）。したがって:

- **対象が要件チケット自体の場合**: 「分解なし単独親」（経路表 #1）の分岐を取る**前に、対象自身の子**を `claude-harness-run check-subtask-completion {対象Issue番号}` で照会する。結果には「取得結果の検証」（下記）を**同じ強度で適用する**——`fallback_truncated` は停止（`decomposition_unverifiable`）、`parent_label_fallback` の候補は本文のヘッダ文法（コードフェンスの外・本文冒頭部の `Parent: #{対象Issue番号}` 行）で再検証する。ただし**自分自身の包含という健全性条件は親方向の照会には適用しない**（子が0件でありうるのが正規のため。健全性条件は「対象自身が子である」証明を持つ実装チケット起動＝兄弟方向の照会にだけ成立する）:
  - **検証済みの子が1件以上** → **分解済みの親への直接起動**として停止する（`parent_already_decomposed`）。実装の単位は子チケットであり、親への全量注入は行わない。停止報告に検証済みの子チケット番号を列挙し、`/para-impl {子番号...}` での再実行を人間に促す。
  - **検証済みの子が0件** → `status` で「検査した結果の0件」と「検査不能」を区別する（スクリプトが両者を分離して返す。仕様の正本はプラグイン配下の `<base>/../../scripts/specs/collect-promotion-context.md`）:
    - **`status: "no_children_found"`（sub-issues API と本文検索の両経路が照会に成功したうえでの0件）**、または文法再検証で全候補が落ちた場合 → 未分解の単独親として扱い、割当不要・新規宣言の全量を当該委譲に含める（経路表 #1）。
    - **`status: "children_lookup_failed"`（照会の失敗を含む0件）→ 停止する**（`decomposition_unverifiable`。取得系の失敗を「未分解」の証明に読み替えない——分解済みの裁可親が一時的な取得失敗の回に「未分解」と誤判定されると、親の全量注入で子チケット群と重複する第2実装が生まれる）。
- **対象が実装チケットの場合**: まず**親の分解の全体像**（全兄弟チケット。今回実装しないものを含む）を `claude-harness-run check-subtask-completion {親Issue番号}` で取得する（Sub-issues API＋`Parent: #<番号>` 本文検索のフォールバック。スクリプトの実行形の規約とランチャー不能時のフォールバックは `references/star-parallel.md`「スクリプトの実行形」と同じ）。

**取得結果の検証（検索は候補列挙・確定は正本文法。検査不能を空集合に丸めない）**:

- **フォールバック結果の文法再検証**: 出力の `source` が `parent_label_fallback` の場合、検索（`Parent: #<番号> in:body`）は本文のどこにマッチしても返す**候補列挙**にすぎず、本ゲート 1-a のヘッダ文法を強制していない。**各候補 Issue の本文を取得し、1-a のヘッダ文法（コードフェンスの外・本文冒頭部の `Parent: #<番号>` 行）で再検証し、通過した Issue だけを兄弟として採用する**（引用・記入例・後段の散文に `Parent: #<番号>` を含むだけの無関係 Issue を分解に混入させない——混入すると保証が無関係チケットへ割り当てられ、または正当な実装が停止する）。`source` が `sub_issues_api` の場合は GitHub の親子リレーションが正本であり、本文文法の再検証は不要。
- **健全性条件（0件は「分解なし」ではない）**: 対象（実装チケット）自身の `Parent: #<番号>` ヘッダが、親に少なくとも1つの子（自分自身）があることを証明している。したがって、**採用後の兄弟集合に対象 Issue 自身が含まれない場合——スクリプトが `no_children_found`（0件）を返した場合を含む——は、「分解なし」に読み替えず検査不能として停止する**（`decomposition_unverifiable`）。スクリプトは照会の失敗を含む0件を `children_lookup_failed` として「検査した結果の0件」（`no_children_found`）と区別して返すが、兄弟方向ではどちらの0件でも「自分自身が含まれない」という矛盾は変わらないため、**0件・自分不在の結果を割当不要（全量注入）の根拠にしない**。
- **打ち切りは完全性の反証**: スクリプトが `status: "fallback_truncated"`（フォールバック検索の結果件数が明示上限に達し、それより多い子が打ち切られている可能性がある）を返した場合、**自分自身が含まれていても停止する**（`decomposition_unverifiable`。欠落した兄弟の AC 候補・依存辺が黙って消え、誤割当になる。件数が上限に達した結果を「全量」として扱わない）。

検証済みの分解が1チケットだけなら、新規宣言の全量がそのチケットの担当である（全数検証は自明に成立）。**分解が複数なら、今回の起動対象が1チケットだけでも、分解の全体像に対して担当割当を解決してから、今回実装するチケットの担当分だけを注入する**——全チケットに親の新規宣言の全量を渡すと、無関係のチケット同士が同じテスト作成・同じ台帳追記を試み、並列 PR の衝突と台帳エントリの重複になる:

- **維持する保証は全チケットに共通で渡す**（抵触チェックは全チケットの実装に必要）。
- **新規宣言する保証は、各 ID をちょうど1つの実装チケットに割り当てる**（**重複割当も未割当も作らない**）。担当チケットだけがその保証のテスト作成と台帳追記（feature-implementer 2-5 の 2・3）を担う。
- **割当は安定入力（親 Issue の保証節・検証済みチケット集合の本文・現行台帳）だけから一意に導出する決定的規則で行う**。割当表は当該実行の実行計画にしか存在せず、別セッションの後続実行は参照できない。したがって**どの実行回でも同じ入力から同じ割当が導出されることだけが、実行間一貫の担保**である（実行内の意味判断・起動順・気分に依存する割当をすると、各回の全数検証は成功するのにどのチケットも当該保証を実装しない取り違えが起こる）。規則は次の3段（**順序・同点の解決まで完全に規定**。**意味的な推測で候補を補わない**——推測は実行回ごとに揺れる）:
  1. **対応 AC の取得**: 各新規宣言行の `（受入基準 AC-n に対応）` 注記から対応 AC を読む（生成規約の正本は `guarantee-section.md` 要件-1）。**注記には複数の AC が列挙されうる**（例: `（受入基準 AC-1, AC-2 に対応）`。生成側は1宣言の複数 AC 対応を禁止していない）——その場合は**列挙された全 AC を読む**。受理するのは `AC-<数字>` の完全一致識別子の列挙（区切りは `,`・`、`）だけであり、**注記が無い・列挙を解釈できない保証は停止**（情報欠落。`guarantee_assignment_unresolvable`）。
  2. **候補の特定（機械一致）**: 検証済みチケット集合の各本文の `対応する受入基準:` ヘッダ行（`implementation-ticket.md` テンプレートの行。分解時に網羅検証済みの割当が転記されている。**1-a と同じヘッダ行の規律——コードフェンスの外・本文冒頭部——で読み、フェンス内・引用の記載を候補判定に使わない**）に、対応 AC が**完全一致**で列挙されているチケットを候補とする。対応 AC が複数ある場合、候補は「**列挙 AC のいずれか**をヘッダ行に持つチケット」の**和集合**とする（積集合にしない——積は候補0件の停止を頻発させ、複数チケットに跨る保証は次段の依存下流タイブレークが最後の統合チケットへ寄せる）。識別子の比較は `AC-<数字>` 全体で行い、`AC-1` を `AC-12` の一部に一致させない。**このヘッダ行を持たないチケットが集合に1つでもある場合は停止**（当該チケットが候補かどうかを機械判定できず、割当の一意性が壊れる。対処は人間による行の追記または `/create-ticket` での再分解）。**候補が0件の保証も停止**（いずれも `guarantee_assignment_unresolvable`）。
  3. **候補からの選択（同点の解決まで規定）**: 候補が1件ならそれ。複数なら、**候補間の依存関係（本文の依存チケット記載。直接・間接を含む）で、依存する他候補の数が最大のチケット**（＝最も下流・最後に完成する側。跨り保証が最後の統合チケットに載る狙いを包含し、この依存は直列化の判断材料に含める）。同数なら**チケット番号が最小のチケット**。
- **既に base の台帳（`docs/guarantees.md`）に登録済みの新規宣言 ID は、先行チケットの実装で担当済み**とみなし、新たな割当対象にしない（逐次実行の後続回で同じ保証を再割当してテスト・台帳追記を重複させない。全数検証では「解決済み」として数える）。**登録済みの ID 集合の取得手順は下記「base リビジョンの台帳の読み取り」が正本**であり、取得できない場合は「未登録」とみなさず停止する（`ledger_unreadable`）。**この登録済み除外は経路によらず全経路に適用する——経路表の「全量」（#1・#2）も「担当分」（#3・#4）も、台帳登録済み ID を除いた集合を指す**（マージ済みチケットの再実行・reopen の回で、登録済みの保証のテスト・台帳追記を重複させない）。
- **割当の全数検証（注入の前に行う）**: 親の新規宣言の各 ID が、**分解の全チケット（今回実装しないものを含む）を通してちょうど1回**割り当てられている（または台帳登録済み＝解決済みである）ことを突き合わせる（0回＝取りこぼし・2回以上＝重複、のどちらも不可）。上記の決定的規則で一意に導出できない ID が1件でもあれば **停止**（`guarantee_assignment_unresolvable`。分解の見直し・チケットの追加・`対応する受入基準:` 行の整備は人間と `/create-ticket` 再実行の判断事項であり、リードが黙って割当を歪めない）。
- 割当表（ID → 担当チケット。各行に対応 AC と適用した選択規則——単独候補・依存下流・番号タイブレーク——を添える）を実行計画に出力し、各チケットへの注入ブロックの新規宣言を**担当分だけ**にする（記録だけにせず注入に接続する）。**実行間の一貫は上記の決定的規則そのものが担保する**——実行計画への出力は当該実行の説明であり、後続実行への引き継ぎ手段ではない（別セッションの後続実行は、同じ安定入力から同じ規則で同じ割当を再導出する）。

#### base リビジョンの台帳の読み取り（登録済み判定の入力）

登録済み判定に使う台帳は、**実装が到達する base リビジョンの内容**である（リードの手元 checkout の台帳を読まない——手元は別ブランチ・stale でありうる。フェーズ判定と同じく、判定の入力は対象（base）の内容を正とする）。

> **台帳の読み取りの正本（この定型文を持つ手順は散文で読み直さない）**: **この定型文が置かれている手順**で台帳から保証 ID・約束文・テスト参照・宣言元を読み取る必要がある場合は、**索引チェック（`guarantee-index-check`）の出力 `guarantees` を使う**こと。**自分で台帳ファイルを開いて数え直さない・Grep のヒットを「登録済み」の根拠にしない**（Grep はコードフェンスも節の範囲も見ないため、台帳が引用している書式の記入例や節の外の言及にマッチする）。散文が独自の規則で同じ台帳を読み直すと、**同じ台帳を2つの規則で読む**状態になり、規則がずれた分だけ欠陥になる（索引チェックはフェンス内を見ないため `status` は `pass` のままで、この食い違いは表に出ない）。フィールド定義の正本はプラグイン配下の `scripts/specs/guarantee-index-check.md`（Read する場合はスキル起動時の「Base directory for this skill」を起点に `<base>/../../scripts/specs/guarantee-index-check.md` として解決すること）。

索引チェックは**台帳のパスを引数で受ける**ため、base リビジョンの台帳を一時ファイルへ書き出して渡す（スクリプト側に追加の機能は要らない。正本: 戦略ドキュメント 5.3「base リビジョンの台帳を読む場合（作業ツリー以外の台帳）」）:

```bash
git show "origin/{base}:docs/guarantees.md" > "<一時ファイル>"
claude-harness-run guarantee-index-check "<一時ファイル>"
```

- **一時ファイルは `mktemp` で作り、判定後に削除する**（作業ツリーへ書き出さない——実装の差分に混ざる）。
- **`git show` の終了コードを確認する**。非0（base に台帳が無い・revision を解決できない）は「未登録」ではなく**検査不能**であり `ledger_unreadable` で停止する（**空出力を「保証0件の台帳」に読み替えない**。リダイレクトは git の成否によらず先に空ファイルを作るため、ファイルの存在を成功の根拠にしない）。
- **スクリプトの実行形とランチャー不能時のフォールバック**は `references/star-parallel.md`「スクリプトの実行形」と同じ規約に従う（先頭トークンと target にパス・バージョン・引用符を付けず、**引数として渡すパスは引用符で囲む**）。
- **`--base` は指定しない**。`--base` はテスト参照の解決基準＝`status` / `broken` にしか効かず、**`guarantees` は参照検査より前に確定する**ため、本手順が消費する `guarantees[].guarantee_id` は `--base` の指定有無・値によらず同一である。一方 `--base` に渡したディレクトリが存在しないと索引チェックは **exit 2** を返し、`ledger_unreadable` で `/para-impl` 全体が停止する。**消費結果に影響しない指定で停止経路だけを増やさない**（この呼び出しの `status` / `broken` を使わないことは次項のとおり）。
- **`index.ledger` が渡した一時ファイルのパスと一致すること**を確認する（別の台帳を読んでいないことの機械的な確認。不一致なら `ledger_unreadable` で停止する）。
- **消費してよいのは `guarantees[].guarantee_id`（登録済み ID の集合）だけ**である。この呼び出しの `status` / `broken` / `counts.broken` は「**base リビジョンの台帳 × 作業ツリーのテストファイル**」という**どちらのリビジョンでもない組み合わせ**の検査結果であり、**索引整合の判定に使わない**（索引整合は作業ツリーを見る `/quality-check` の索引ゲートが担う）。したがって **`status` が `"fail"` であることを理由に停止しない**——登録済み判定に必要な `guarantees` は exit 0 / exit 1 のどちらでも stdout に出力される。
- **exit 2（台帳を読めない・`## 保証` 節が無い・`jq` 不在・引数不正）／stdout が空またはパース不能／スクリプト実行不能** → `ledger_unreadable` で停止する。**`guarantees` を空集合に丸めて重複割当の検査を素通りさせない**。
- **`guarantees` に現れない見出しを「登録済み」とみなさない**（ID 書式違反＝`broken` の `malformed_guarantee_id`・「保証」節の外＝`guarantee_outside_section`）。登録済みでない ID は割当対象に残るのが安全側であり、ここで「登録済み」に倒すとその保証を誰も実装しない。

**経路の表（対象の構造 × 起動形態の全経路。受理方向を含めこの表が網羅の正本）**:

| # | 対象の構造 | 今回の起動 | 割当 | 注入する新規宣言 | 扱い |
|---|---|---|---|---|---|
| 1 | 要件チケット自体で、対象自身の子照会（検証済み）が0件（未分解） | 単独 | 不要 | 親の全量 | 受理 |
| 2 | 親が1チケットのみに分解 | 当該1件 | 自明（全量がその1チケットの担当。全数検証は成立） | 全量 | 受理 |
| 3 | 親が複数チケットに分解 | 複数を同時実装（star 型・直列） | 必須（分解の全チケット横断で全数検証） | 各チケットの担当分のみ | 受理 |
| 4 | 親が複数チケットに分解 | 1チケットだけ起動（逐次実行） | 必須（分解の全体像で割当を解決してから） | 当該チケットの担当分のみ | 受理 |

### 転記の規律

- 転記対象は**「### 新たに宣言する保証」「### 維持する保証」の2カテゴリだけ**（「### 判定保留（要人間判定）」は機械処理の対象外であり注入しない。下流の `/promote-verify` と同じ線引き）。
- **維持する保証は全チケット共通・逐語で転記する**（要約・言い換え・並べ替えをしない。`- なし` の明示もそのまま転記する——「なし」は検査した結果の0件であり、行を省くと受け手が「調べていない」と区別できない）。ただし**維持の約束文の判定根拠は転記ではなく現行の保証台帳**（`docs/guarantees.md`）である——転記は人間レビュー用であり、約束文の正は常に台帳（正本: `guarantee-section.md` 維持の規定）。抵触確認時の台帳での解決・ID 不在／文面ドリフトの停止は feature-implementer 2-5 が行う。
- **新規宣言する保証は担当割当に従い、当該チケットの担当分の行だけを転記する**（行単位の抜粋であり、**行内は逐語**——約束文の言い換え・ID の改変をしない。担当が0件のチケットには `- なし` を書く。親の新規宣言そのものが `- なし` の場合も同様）。
- **同一性の検証（転記の前に行う）**: 新規宣言の各 ID が `G-<裁可対象Issue番号>-<枝番>` の**完全文法**（`<枝番>` は1文字以上の数字だけ）に一致することを、ハイフンまで含めた比較で確認する（`G-158-` と `G-1580-` を取り違えない。**接頭辞一致で通さない**）。不一致 → **停止**（`guarantee_scope_mismatch`。裁可時の検証をすり抜けた壊れた保証節であり、注入せず人間に差し戻す）。
- 保証節が無い・解釈できない → **停止**（`guarantee_section_unreadable`）。**注入を省略して実装へ進まない**（保証節の不在・読み取り不能を「保証なし」に丸めない。`guarantee:approved` が付いているのに節を読めないのは運用前提の破れ）。
- Phase 4-5 の停止も 1-d の「停止時の報告」と同じ形式で報告する（`判定` 列は `停止`、`reason` は語彙表の Phase 4-5 のコード）。

### 委譲プロンプトへの記載形式

```text
【保証節（GDD期・裁可対象 Issue #{番号} より逐語転記）】

### 新たに宣言する保証

{当該チケットの担当分の行だけを逐語転記（担当割当は全数検証済み。担当0件なら - なし）}

### 維持する保証

{当該カテゴリ配下を逐語転記（全チケット共通）}

このブロックに基づき「2-5. 保証整合確認」（feature-implementer の Phase 2）を実施すること。
```

### star 型（複数Issue）での伝播

リードは worker の spawn プロンプトにこのブロック（Issue ごとに当該 Issue の裁可対象のもの）を含め、worker は `feature-implementer` への委譲プロンプトへ**そのまま逐語で引き継ぐ**。**合流ゲート伝播条項の逐語転記の規定はそのまま維持し、本ブロックはそれと並記で追加する**（条項の規定・文言には触れない）。
