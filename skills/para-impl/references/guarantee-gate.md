# 裁可ゲートと保証ブリーフ（GDD期のみ）

> 参照パスは `${CLAUDE_PLUGIN_ROOT}` 配下です（例: `${CLAUDE_PLUGIN_ROOT}/skills/para-impl/references/guarantee-gate.md`）。Read にはプラグインの絶対パスが必要です（スキル起動時の「Base directory for this skill」を起点に解決する）。

保証台帳（`docs/guarantees.md`）を駆動文書とする GDD期のプロジェクトでのみ実行する追加手順。**Phase 1 では対象 Issue（実装チケットなら親）の裁可（`guarantee:approved`）を確認し、無ければ実装を開始せず停止して人間の裁可を促す**。**Phase 4-5 では裁可対象（親）Issue の保証節（新規宣言＋維持）を `feature-implementer` への委譲プロンプトに含める**。

> **本ファイルの前提**: 開発フェーズの判定（`detect-dev-phase` の実行と `sdd` / `gdd` / `invalid` の分岐、`sdd` のときに本ファイルを読まずに従来手順だけを行うこと）は SKILL.md 側で完了している前提で読むこと。**`sdd`（フェーズ宣言なしを含む）で本ファイルの手順を一切実行しない規律と、`invalid`・判定不能で中断する規律は SKILL.md が正本**であり、本ファイルには複製しない。

裁可ラベルの語彙（`guarantee:proposed` / `guarantee:approved`）と運用（付与は人間のみ・裁可の単位は親 Issue）の正本は `<base>/../create-ticket/references/guarantee-section.md`（要件-3・分解-2）。**本スキルはゲートの強制（`guarantee:approved` が無ければ実装を始めない）を担い、`guarantee:approved` を自分で付けない**（裁可は人間の行為であり、ゲートの強制者が自分で解錠する経路を作らない）。**ラベル定義の作成もしない**（定義の用意は `/create-ticket` の責務）。

## Phase 1: 裁可ゲート（前提未充足での停止）

**統合ブランチ存在チェックと同じ「前提未充足での停止」パターンを使う**——満たされていなければ処理を止め、人間が行う操作を示して終了する。**新しい待ち合わせ機構（裁可待ちのポーリング・ラベル変更の監視）は作らない**。

### 1-a. 裁可対象の解決（対象 Issue ごと）

Phase 1 で取得済みの各 Issue 本文の冒頭ヘッダ行（テンプレート `implementation-ticket.md` の書式 `Parent: #{親チケット番号}`・`保証: 親#{親チケット番号} の保証節参照`）から裁可対象を決める。ヘッダ行はコードフェンスの外・本文冒頭部にあるものだけを読む（本文中の引用・書式例を拾わない）:

| 本文の状態 | 裁可対象 |
|---|---|
| `Parent: #<N>` 行と `保証: 親#<M> の保証節参照` 行があり N = M | 親 Issue `#<N>` |
| `Parent: #<N>` 行のみ（`保証:` 行なし） | 親 Issue `#<N>` |
| `保証: 親#<M> の保証節参照` 行のみ | 親 Issue `#<M>` |
| どちらの行も無い（要件チケット・単独タスク） | 対象 Issue 自身 |
| `Parent: #<N>` と `保証: 親#<M>` の番号が食い違う（N ≠ M） | **解決不能**（判定表 #1。どちらかを勝手に採用しない） |

### 1-b. ラベルの取得と判定

裁可対象ごとに `gh issue view {裁可対象番号} --json labels` でラベル一覧を取得し、`name` の**完全一致**で判定する（**接頭辞・部分一致で通さない**。別ラベルや似た名前のラベルを裁可と誤認しない）。

**判定表（各行は排他。上から順に評価し、最初に該当した行で確定する）**:

| # | 状態 | 動作 | `reason` |
|---|---|---|---|
| 1 | 裁可対象を解決できない（`Parent:` 行と `保証:` 行の親番号の食い違い） | **停止**（同一性が成立しない Issue を実装しない） | `parent_mismatch` |
| 2 | ラベル一覧を取得できない（Issue が存在しない・取得エラー・出力がパース不能） | **停止**（**検査不能を「ラベルなし」に読み替えない**。報告では「確認できず」と裁可待ちを区別する） | `labels_unavailable` |
| 3 | `guarantee:approved` と `guarantee:proposed` の両方が付いている | **停止**（裁可の付け替え——`guarantee:proposed` を外す——が完了していない中間状態。裁可済みとみなさない） | `label_state_ambiguous` |
| 4 | `guarantee:approved` が完全一致で付いている（`guarantee:proposed` は無い） | **ゲート通過**（当該 Issue は実装してよい） | — |
| 5 | `guarantee:approved` が無い（`guarantee:proposed` のみ・どちらも無いを含む） | **停止**（人間の裁可待ち） | `approval_missing` |

### 1-c. 複数 Issue の扱い（部分成功≠完全成功）

- **全対象 Issue の判定を先に終えてから**次へ進む（1件目の停止で残りの判定を打ち切らず、停止報告に全 Issue の判定結果を列挙する）。
- **1件でも「停止」に該当する Issue があれば、Phase 2 以降へ進まず全体を停止する**（裁可済みの Issue だけを先に実装しない。裁可漏れはチケット分解・裁可運用の異常の兆候であり、部分実行すると停止分の扱いが宙に浮く）。
- 判定できなかった Issue（`labels_unavailable`）を「問題なし」に数えない。

### 1-d. 停止時の報告（すべての `reason` に共通。項目を省略・推測で埋めない）

```text
## 実装を開始していません（GDD期・裁可ゲート未通過）

| 対象 Issue | 裁可対象 | 判定 | reason | 現在のラベル |
|---|---|---|---|---|
| #{番号} | #{裁可対象番号} | 通過 / 停止 | {reason コード} / — | {ラベル一覧。取得できなければ「確認できず」} |

- 人間が行う操作: 裁可対象 Issue の保証節をレビューし、承認するなら `guarantee:proposed` を外して `guarantee:approved` に付け替える（GitHub の UI から、または gh issue edit のラベル操作で行う。付け替えは人間の操作であり、このコマンドをエージェントが代行しない）
- 裁可後の再開: /para-impl {対象 Issue 番号} を再実行する
```

**`reason` コードの語彙（この表が正本。増減するときは判定表・停止時の報告・Phase 4-5 の停止条件を必ず同時に更新する）**:

| `reason` | 適用フェーズ | 停止する条件 |
|---|---|---|
| `parent_mismatch` | Phase 1 | `Parent:` 行と `保証:` 行の親 Issue 番号が食い違い、裁可対象を解決できない |
| `labels_unavailable` | Phase 1 | 裁可対象のラベル一覧を取得できない（検査不能。「ラベルなし」に読み替えない） |
| `label_state_ambiguous` | Phase 1 | `guarantee:approved` と `guarantee:proposed` が同時に付いている |
| `approval_missing` | Phase 1 | `guarantee:approved` が付いていない（人間の裁可待ち） |
| `guarantee_section_unreadable` | Phase 4-5 | 裁可対象の本文に保証節が無い・親Issue本文の文法で解釈できない（裁可済みなのに節を読めないのは運用前提の破れ） |
| `guarantee_scope_mismatch` | Phase 4-5 | 新規宣言の ID が `G-<裁可対象番号>-<枝番>` の完全文法に一致しない |
| `guarantee_assignment_unresolvable` | Phase 4-5 | 新規宣言の担当割当で、どの実装チケットにも割り当てられない・単独で検証可能にできない ID がある |

## Phase 4-5: 保証節の注入（保証ブリーフ）

リードは「クリティカル設計決定」セクションと同様に、**裁可対象（親）Issue の保証節（新規宣言＋維持）を `feature-implementer` への委譲プロンプトに含める**。

### 読み取り文法（3つ目の独自解釈を作らない）

裁可対象 Issue 本文の保証節の読み取り文法の**正本は `<base>/../create-ticket/references/guarantee-section.md` の「共通-2. 読み取り規則」**——(a) 文法に依存しない共通部分と (c) 親Issue本文の文法——であり、Read して従うこと（**(b) 台帳の文法を親Issue本文へ適用しない**）。下流の `/promote-verify`（Step 5.5-3）も同じ文法で読む。**本ファイルには文法を複製しない**（生成側・検証側・注入側が同じ1つの規則を読む）。

### 新規宣言の担当割当（親が複数の実装チケットに分解されている場合）

**割当の要否は、今回の起動形態（同時か1件ずつか・star 型か単独か）ではなく、裁可対象（親）の構造——親が複数の実装チケットに分解されているか——で決める。** 起動形態で決めると、分解済みの親に対して 1 チケットだけを逐次起動した回で親の新規宣言の全量が注入され、後で別の子を実行したときに同じテスト作成・同じ台帳追記・ID の重複が再発する。

対象 Issue が要件チケット自体（実装チケットに分解されていない）の場合は割当不要であり、新規宣言の全量を当該委譲に含める。対象 Issue が実装チケットの場合は、まず**親の分解の全体像**（全兄弟チケット。今回実装しないものを含む）を `claude-harness-run check-subtask-completion {親Issue番号}` で取得する（Sub-issues API＋`Parent: #<番号>` 本文検索のフォールバック。スクリプトの実行形の規約とランチャー不能時のフォールバックは `references/star-parallel.md`「スクリプトの実行形」と同じ）。分解が1チケットだけなら、新規宣言の全量がそのチケットの担当である（全数検証は自明に成立）。**分解が複数なら、今回の起動対象が1チケットだけでも、分解の全体像に対して担当割当を解決してから、今回実装するチケットの担当分だけを注入する**——全チケットに親の新規宣言の全量を渡すと、無関係のチケット同士が同じテスト作成・同じ台帳追記を試み、並列 PR の衝突と台帳エントリの重複になる:

- **維持する保証は全チケットに共通で渡す**（抵触チェックは全チケットの実装に必要）。
- **新規宣言する保証は、各 ID をちょうど1つの実装チケットに割り当てる**（**重複割当も未割当も作らない**）。担当チケットだけがその保証のテスト作成と台帳追記（feature-implementer 2-5 の 2・3）を担う。
- 割当の材料: 約束文の `（受入基準 AC-n に対応）` 注記と、各実装チケットの完了条件・変更対象。**その保証のテストを当該チケットの変更だけで成立させられるチケット**へ割り当てる。複数チケットに跨って初めて成立する保証は、依存順で最後に完成するチケットへ割り当てる（この依存は直列化の判断材料に含める）。
- **既に現行台帳（`docs/guarantees.md`）に登録済みの新規宣言 ID は、先行チケットの実装で担当済み**とみなし、新たな割当対象にしない（逐次実行の後続回で同じ保証を再割当してテスト・台帳追記を重複させない。全数検証では「解決済み」として数える）。
- **割当の全数検証（注入の前に行う）**: 親の新規宣言の各 ID が、**分解の全チケット（今回実装しないものを含む）を通してちょうど1回**割り当てられている（または台帳登録済み＝解決済みである）ことを突き合わせる（0回＝取りこぼし・2回以上＝重複、のどちらも不可）。どのチケットにも割り当てられない・単独で検証可能にできない ID が1件でもあれば **停止**（`guarantee_assignment_unresolvable`。分解の見直し・チケットの追加は人間と `/create-ticket` 再実行の判断事項であり、リードが黙って割当を歪めない）。
- 割当表（ID → 担当チケット）を、割当の根拠（AC 対応・完了条件との対応）とあわせて実行計画に出力し、各チケットへの注入ブロックの新規宣言を**担当分だけ**にする（記録だけにせず注入に接続する。根拠の記録は、後で別の子を逐次実行する回が同じ割当を再現するための材料になる）。

**経路の表（対象の構造 × 起動形態の全経路。受理方向を含めこの表が網羅の正本）**:

| # | 対象の構造 | 今回の起動 | 割当 | 注入する新規宣言 | 扱い |
|---|---|---|---|---|---|
| 1 | 要件チケット自体（実装チケットに分解されていない） | 単独 | 不要 | 親の全量 | 受理 |
| 2 | 親が1チケットのみに分解 | 当該1件 | 自明（全量がその1チケットの担当。全数検証は成立） | 全量 | 受理 |
| 3 | 親が複数チケットに分解 | 複数を同時実装（star 型・直列） | 必須（分解の全チケット横断で全数検証） | 各チケットの担当分のみ | 受理 |
| 4 | 親が複数チケットに分解 | 1チケットだけ起動（逐次実行） | 必須（分解の全体像で割当を解決してから） | 当該チケットの担当分のみ | 受理 |
| 5 | 新規宣言が `- なし` | いずれでも | 対象0件（割当不要） | `- なし` | 受理 |
| 6 | 割当を解決できない ID がある（どのチケットにも対応しない・単独検証不能） | いずれでも | 解決不能 | 注入しない | **停止**（`guarantee_assignment_unresolvable`） |

### 転記の規律

- 転記対象は**「### 新たに宣言する保証」「### 維持する保証」の2カテゴリだけ**（「### 判定保留（要人間判定）」は機械処理の対象外であり注入しない。下流の `/promote-verify` と同じ線引き）。
- **維持する保証は全チケット共通・逐語で転記する**（要約・言い換え・並べ替えをしない。`- なし` の明示もそのまま転記する——「なし」は検査した結果の0件であり、行を省くと受け手が「調べていない」と区別できない）。ただし**維持の約束文の判定根拠は転記ではなく現行の保証台帳**（`docs/guarantees.md`）である——転記は人間レビュー用であり、約束文の正は常に台帳（正本: `guarantee-section.md` 維持の規定）。抵触確認時の台帳での解決・ID 不在／文面ドリフトの停止は feature-implementer 2-5 が行う。
- **新規宣言する保証は担当割当に従い、当該チケットの担当分の行だけを転記する**（行単位の抜粋であり、**行内は逐語**——約束文の言い換え・ID の改変をしない。担当が0件のチケットには `- なし` を書く。親の新規宣言そのものが `- なし` の場合も同様）。
- **同一性の検証（転記の前に行う）**: 新規宣言の各 ID が `G-<裁可対象Issue番号>-<枝番>` の**完全文法**（`<枝番>` は1文字以上の数字だけ）に一致することを、ハイフンまで含めた比較で確認する（`G-158-` と `G-1580-` を取り違えない。**接頭辞一致で通さない**）。不一致 → **停止**（`guarantee_scope_mismatch`。裁可時の検証をすり抜けた壊れた保証節であり、注入せず人間に差し戻す）。
- 保証節が無い・解釈できない → **停止**（`guarantee_section_unreadable`）。**注入を省略して実装へ進まない**（保証節の不在・読み取り不能を「保証なし」に丸めない。`guarantee:approved` が付いているのに節を読めないのは運用前提の破れ）。
- Phase 4-5 の停止も 1-d の「停止時の報告」と同じ形式で報告する（`判定` 列は `停止`、`reason` は語彙表の Phase 4-5 のコード）。

### 委譲プロンプトへの記載形式

```text
【保証節（GDD期・裁可対象 Issue #{番号} より逐語転記）】

### 新たに宣言する保証

{当該チケットの担当分の行だけを逐語転記（担当割当は全数検証済み。担当0件なら - なし）}

### 維持する保証

{当該カテゴリ配下を逐語転記（全チケット共通）}

このブロックに基づき「2-5. 保証整合確認」（feature-implementer の Phase 2）を実施すること。
```

### star 型（複数Issue）での伝播

リードは worker の spawn プロンプトにこのブロック（Issue ごとに当該 Issue の裁可対象のもの）を含め、worker は `feature-implementer` への委譲プロンプトへ**そのまま逐語で引き継ぐ**。**合流ゲート伝播条項の逐語転記の規定はそのまま維持し、本ブロックはそれと並記で追加する**（条項の規定・文言には触れない）。
